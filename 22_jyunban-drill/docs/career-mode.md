# キャリアモード設計メモ

実装した段階・ポイント閾値・保存仕様は [`implementation-design.md`](implementation-design.md) を参照してください。

## 1. 目的

「順番のセンス」のキャリアモードは、問題を解いて得たポイントを、キャラクターの仕事や日々の変化として感じられるようにするための小さな物語要素です。

職種名や肩書きが変わることだけを成長として扱うのではなく、**同じ仕事の中で、できること・見えること・周囲との関わり方が少しずつ変わる**ことを大切にします。

このドリルで文章の順番を練習することが、仕事の場面で「状況を整理する」「相手に伝わる形で説明する」「問題の背景を考える」といった変化につながる。その手応えを、フレーバーテキストで表現します。

## 2. 基本方針

- 職種そのものに上下をつけない。コールセンター、テスト、キッティング、運用などを「価値の低い仕事」として描かない。
- 困難の原因は、仕事の価値ではなく、経験を次にどうつなげるかが見えないことや、情報共有・説明・判断にまだ慣れていないこととして描く。
- 成長は「他人からの評価」だけでなく、「自分で気づく」「自分から改善する」ことでも表現する。
- いつも上司や顧客を悪役にしない。厳しい言葉や失敗も描くが、後から本人が状況を捉え直せる余地を残す。
- フレーバーテキストは短く、仕事の場面が想像できる具体的な言葉にする。
- ポイントやランクは遊びのための指標であり、現実の能力・職位・市場価値を評価するものではない。
- 一度の失敗でキャリアが後退したり、ポイントを失ったりしない。

## 3. 成長を表す3つの変化

キャリアの変化は、次の3つを組み合わせます。

1. **他人からの評価**：怒られた、指摘された、助かったと言われた。
2. **自分で気づく**：何が伝わっていなかったのか、何を先に確認すればよいのかが分かる。
3. **自分から改善する**：報告の仕方を変える、繰り返す問題を見つける、関係者に提案する。

初期は他人の反応に振り回されがちでも、経験を積むにつれて、自分で状況を整理し、次に取る行動を考えられるようになる流れを意識します。

## 4. 同じ職種の中で変化する例

### コールセンター業務

| 段階 | フレーバーテキスト | 変化のポイント |
|---|---|---|
| 初期 | 「お前じゃ話にならない。上司に代われと言われた。」 | 相手の困りごとを整理できず、会話を引き継ぐしかない。 |
| 慣れ始め | 「上司に代わる前に、状況くらい聞いておいてくれと言われた。」 | 発生したこと、利用環境、困っていることを順に聞く。 |
| 安定 | 「最近、あなたからの引き継ぎは分かりやすいねと言われた。」 | 担当者が次に何をすればよいか分かる形で情報を渡せる。 |
| 自発的な改善 | 「同じ質問が何度も来る。これ、案内の文章が分かりにくいんじゃないか？」 | 個別対応だけでなく、繰り返し起きる問題を見つけて改善につなげる。 |

### テスト・試験業務

| 段階 | フレーバーテキスト | 変化のポイント |
|---|---|---|
| 初期 | 「障害票の報告が分からないと、プログラマーに文句を言われた。」 | 不具合を見つけても、相手が調査できる形で伝えられない。 |
| 慣れ始め | 「『再現手順を書いて』と言われたけど、どこまで書けばいいんだろう。」 | 操作、発生条件、期待した結果、実際の結果を整理する。 |
| 安定 | 「この障害票なら、再現できるって返事が来た。」 | 読んだ人が同じ状況を再現できる報告を書く。 |
| 自発的な改善 | 「この画面、毎回ここで迷う。テスト項目だけじゃなく、仕様も確認した方がよさそうだ。」 | 不具合の記録にとどまらず、仕様や利用者の動きにも目を向ける。 |

### キッティング・端末準備

| 段階 | フレーバーテキスト | 変化のポイント |
|---|---|---|
| 初期 | 「手順書どおりにやったのに、端末が使えないと言われた。」 | 手順の実施と、完了状態の確認がつながっていない。 |
| 慣れ始め | 「最後に確認する項目を、チェックリストにしておこう。」 | 作業の抜け漏れを防ぐため、確認内容を整理する。 |
| 安定 | 「この端末だけ設定が違う。先に条件を確認しておいてよかった。」 | 例外条件を意識し、作業前に確認できる。 |
| 自発的な改善 | 「毎回同じところで止まるなら、手順書の順番を変えた方がよさそうだ。」 | 作業をこなすだけでなく、手順自体を改善する。 |

※ 文言は初期案です。実際の問題や対象読者に合わせて、きつさ・現実味・読みやすさを調整します。

## 5. 職種をまたぐ変化

キャリア全体の流れを描く場合も、職種の序列ではなく、経験をどう次の仕事につなげるかを軸にします。

| キャリア上の場面 | 状況の例 | 次につながる経験 |
|---|---|---|
| アサイン待ち | 「来月から何をするのか、まだ決まっていない。」 | 自分が学んだことや、次に経験したいことを整理する。 |
| コールセンター業務 | 「問い合わせには答えられる。でも、技術的な質問は取り次ぐしかない。」 | 相手の状況を聞き取り、情報を整理して引き継ぐ。 |
| テスト・試験業務 | 「障害票の報告が分からないと、プログラマーに文句を言われた。」 | 再現手順や期待結果を整理し、調査できる報告を書く。 |
| キッティング・端末準備 | 「手順どおりにはできる。でも、なぜその作業が必要なのかは、まだよく分からない。」 | 作業の目的や例外条件を理解し、手順の意味を考える。 |
| 運用・保守 | 「障害の一次対応はできるようになった。でも、原因の説明は難しい。」 | 発生状況、影響範囲、対応内容を整理して説明する。 |
| 開発補助・実装 | 「コードは直せた。でも、なぜ直したのかを説明できなかった。」 | 変更の目的や影響を言葉にして伝える。 |
| 設計・仕様整理 | 「実装を始めてから、そもそも要求が曖昧だったことに気づいた。」 | 要求、制約、例外条件を整理してから設計する。 |
| 要件整理・全体設計 | 「作るものだけでなく、なぜ作るのか、誰が困っているのかから考えられるようになった。」 | 利用者や関係者の目的を整理し、全体像を考える。 |

この表は職種の優劣や、誰もがこの順番で進むべきという標準キャリアを示すものではありません。現実には行き来や並行があり、どの仕事にも専門性があります。ドリル内では、仕事の見通しや経験のつながりが少しずつ見えてくる物語として使います。

## 6. 表示・進行の考え方

- 初期状態は、必ずしも「貧しい」「何も持っていない」といった生活水準の低さで表現しない。
- 物語の出発点を「アサイン待ち」など先が見えにくい状態にする場合は、本人の価値を低く見せるのではなく、次の仕事や経験につながる道筋が見えない不安として描く。
- 同じ職種の中で複数段階を設け、一定ポイントごとに短いエピソードが変化する設計も検討する。
- 肩書きや部屋の変化は、職業的な昇進を直接模倣するのではなく、積み重ねを楽しむ補助要素として扱う。
- 初期リリースでは画像を必須にせず、短いテキストだけで成立させる。

## 7. 実装で決めたこと

- エピソードは累積ポイントで10段階に解放し、具体的な閾値と文章は [`implementation-design.md`](implementation-design.md) にまとめます。
- 肩書きと部屋の短文はホーム画面のキャリア欄に常時表示します。ポイントが増えた後はその時点のエピソードに切り替わり、過去エピソードの一覧は初期実装には含めません。
- 職種をまたぐ物語は一例であり、標準キャリアや職種の序列を示すものではありません。
- 表示タイトルはドリル内の物語上の呼び名です。「プレイングマネジャー」を個人貢献者より上位の働き方として扱いません。
- 失敗によるポイント減少、降格、連続日数の減点はありません。
- 表現の調整や職種内の追加エピソードは、利用時の読みやすさを見て今後検討します。

## 8. 目指す体験

最初は、言われたことにうまく答えられず、何が悪かったのかも分からない。少しずつ情報を整理して伝えられるようになり、やがて自分で問題の背景に気づき、改善を提案できるようになる。

**肩書きが立派になることよりも、仕事の見え方が変わっていくこと。** それを、短いエピソードの積み重ねで表現します。
