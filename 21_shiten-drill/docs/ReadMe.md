# 視点ドリル (shiten-drill)

外部設計・仕様書を書くときの「システム目線」「ユーザー目線」の書き分けを鍛える問題集サイト。

「図解ドリル（zukai-drill）」の姉妹編。

## 背景・コンセプト

すべての人が読みやすいドキュメントというのは存在しない。誰が読むかによって、書くべき視点は変わる。

「開発者視点」「顧客視点」のように実在の人物を軸に考えると、「気持ちが分からない」といった具合に話が発散してしまう。

そこでITドキュメントの基本として使われるのが「システム目線」「ユーザー目線」という2つの軸。仕様書の中でこの2つが書き分けられていないと、読み手（実装者／レビュアー／クライアント）ごとに負担がかかる。

一度身につければずっと使える概念なので、問題を解きながら体に入れてもらう。

### スコープについて

このドリルは「システム目線 ⇔ ユーザー目線」の書き分けに特化している。開発者視点・顧客視点のような「誰が読むか」の違いはあえて扱わない（別レイヤーの話であり、混ぜると練習として発散するため）。

## 出題形式

1. **変換問題（システム→ユーザー）**：システム目線の一文を提示し、ユーザー目線に書き換えさせる
2. **変換問題（ユーザー→システム）**：ユーザー目線の一文から、背後にある仕様をシステム目線で書かせる
3. **分類問題**：両方の文を見せて、仕様書のどのセクション（機能要件／UI要件／非機能要件など）に向いているかを選ばせる

## 見分け方のコツ（解説用メモ）

- **主語チェック**：主語が「システムは」「処理は」ならシステム目線。主語が「ユーザーは」「画面には」ならユーザー目線。
- **「誰が読むか」で決める**：開発者・テストが読む機能仕様のコアはシステム目線（処理・条件・データ構造・エラーコードなど実装できる粒度）。UI仕様や受け入れ基準はユーザー目線（見える結果・体験ベース）。
- **非機能要件は基本システム目線一択**：性能・セキュリティ・データ整合性などユーザーに直接見えない制約は、無理にユーザー目線へ翻訳しない。
- **受け入れ条件・テストケースはユーザー目線が起点**：「ユーザーが何をしたら何が起きるべきか」から書き、それを支える内部処理をシステム目線で紐づける（Given-When-Thenに近い発想）。
- **読み手の立場で寄せる**：クライアント／コンサル向けの説明資料はユーザー目線寄り、自社エンジニア向けの指示書はシステム目線寄りにすると、同じ仕様でも読み手の負担が減る。

## 問題サンプル（10問）

| # | システム目線 | ユーザー目線 |
|---|---|---|
| 1 | ログインID・パスワードの認証に失敗した場合、エラーコード401を返却する。 | ID・パスワードが間違っていると、画面にエラーメッセージが表示され、再入力を求められる。 |
| 2 | 入力フォームの必須項目が未入力の場合、送信ボタン押下時にバリデーションエラーを発生させる。 | 必須項目を入力し忘れたまま送信しようとすると、どこが未入力か赤字で教えてくれる。 |
| 3 | セッションタイムアウトは最終操作から30分後に設定する。 | 30分操作しないでいると、自動的にログアウトされてしまう。 |
| 4 | 検索処理はElasticsearchのインデックスに対して全文検索クエリを実行する。 | キーワードを入れて検索すると、関連する商品がすぐに一覧で出てくる。 |
| 5 | バッチ処理は毎日午前3時に起動し、前日分の売上データを集計する。 | 朝出社すると、前日の売上レポートがすでに出来上がっている。 |
| 6 | ファイルアップロードは最大10MB、拡張子はjpg/png/pdfのみ許可する。 | 大きすぎるファイルや対応していない形式を選ぶと、アップロードできない理由を教えてくれる。 |
| 7 | 注文確定時にDBトランザクションを開始し、在庫テーブルをロックして更新する。 | 注文を確定すると、他の人と同時に買っても在庫がマイナスになったりしない。 |
| 8 | 権限テーブルのロールIDに基づき、管理画面の表示項目を出し分ける。 | 自分の役職に応じて、見える機能・見えない機能が変わる。 |
| 9 | APIのレスポンスタイムが3秒を超えた場合、タイムアウトエラーを返す。 | 読み込みが遅いと、いつまでも待たされずにエラーで教えてもらえる。 |
| 10 | パスワードはbcryptでハッシュ化してDBに保存する。 | パスワードは安全に保管されていて、もし情報が漏れても中身は読み取られない。 |
