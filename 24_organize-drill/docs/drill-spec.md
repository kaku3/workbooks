# 設計ドリルへの調整方針

## 目的と画面の役割

「図で整理ドリル」を、要求仕様とヒアリングメモを読み、要件定義・外部設計の内容を図に整理する設計ドリルとして調整する。

- 上部：依頼者が実現したいことを、要求仕様として提示する。
- 左側：要求仕様を聞き出し、要件定義・外部設計を整理している途中のメモを付箋で提示する。必要性や関係は学習者が判断する。
- 右側：メモを根拠に、必要な解答カードを選び、処理・判断・通知などの関係を図にする。

この文書は調整方針を定める。以下に沿って画面・全50問の問題データ・生成処理を更新した。本文の意味と正解の整合は、問題別レビュー資料で引き続き確認する。

## 現状の課題

- `promptInstruction` は `prompt.intro` と `prompt.task` を連結しており、資料の説明と操作指示が中心で、依頼者の要求が伝わりにくい。
- 付箋に「外部設計｜処理順序」「詳細設計｜内部処理」などの見出しがあり、整理途中のメモというより完成した設計資料に見える。
- `build-documents.mjs` が正解の `connections` とカードラベルから「Aの次はB」を生成している。付箋と矢印が直接対応するため、設計上の判断をせずに解答できる。
- 対象外の付箋には「別紙を参照」「別途確認」「今回の図では扱わない」などが多く、具体的な要求を読んで範囲を判断する練習になりにくい。
- 左側は付箋を動かせるが、不要と判断した情報をゴミ箱に整理できない。

## 上部には要求仕様を書く

`promptInstruction` には、業務上の目的、利用者、実現したい振る舞い、今回図にする範囲を書く。問題ごとの要求仕様を `prompt.requirements` として持たせ、表示元を明確にする。

操作説明は共通の案内に置く。要求仕様の本文に「付箋を選んで矢印でつなぐ」といった操作指示を混ぜない。

要求仕様は正解の処理を順番に列挙する文章にしない。全体の目的と対象範囲を示し、詳細な条件や役割は左側のメモから読み取れるようにする。

例：システム権限の申請

> 社員が業務に必要なシステム権限を申請できるようにしたい。業務上の必要性と利用可能な権限を確認したうえで付与し、申請者が結果を把握できること。今回の図では、申請を受け付けてから結果を知らせるまでの業務の流れを整理する。

## 左側の付箋は整理途中のメモにする

### 見出しと見た目

- 付箋上の見出しを削除し、本文だけを表示する。「外部設計」「処理順序」「運用メモ」などの別名への置き換えはしない。
- `title` がレビュー資料などで必要な場合は内部情報として残せるが、画面には表示しない。
- `kind` や `covers` は作問・検証用の情報として保持する。必要／対象外や設計工程が色から分からないよう、付箋の色は意味分類と切り離す。
- 1枚につき、ひとつの論点を短い文章で記す。業務用語、依頼者の要望、確認で分かった制約などを具体的に書く。

### 正解を写す文章から、判断の根拠へ変える

「Aを行った後にBへ進む」という接続の言い換えを中心にせず、目的・担当・前提条件・入力と結果・例外時の扱いを記す。学習者が複数のメモを照合して、必要な要素と関係を組み立てられるようにする。

| 現在の文章 | 調整後の文章例 | 読み取る内容 |
| --- | --- | --- |
| 「社員が権限を申請」が終わったら、「上長が必要性を確認」に移る。 | 申請には利用したいシステムと業務上の理由を書いてもらう。理由の妥当性は、その社員の上長が確認する。 | 申請内容と上長の確認の関係 |
| 「上長が必要性を確認」を受けて、「管理者が権限範囲を確認」につなぐ。 | 管理者が権限の範囲を確認する対象は、上長が業務上必要と認めた申請とする。 | 管理者による確認の前提 |
| 「管理者が権限範囲を確認」の次は「権限を付与」を行う。 | 業務上必要でも、そのまま希望どおりの権限を付けられるとは限らない。付与する権限は、管理者が確認した範囲に限る。 | 権限付与に必要な確認 |
| 「権限を付与」が終わったら、「申請者へ結果を通知」に移る。 | 申請者への連絡には、実際に付与できた権限を載せる。 | 通知に必要な確定情報 |

これらは文章の粒度を示す例であり、全問に同じ定型文を当てはめない。順序が要求として明示されている場合は自然に記載するが、全接続を1本ずつ説明する構成にはしない。

分岐は条件と各結果、やり直しは再入力・再確認が必要になる理由、並行処理はそれぞれの開始条件や相互の待ち合わせの有無を書く。表現を曖昧にすることで難しくせず、図を決める根拠を残す。

### 対象外の情報も具体的な要求にする

対象外の付箋も、同じ業務についてヒアリングした内容にする。要求としては意味があるが、上部で示した今回の図の範囲には入らない情報を混ぜる。

- 「権限画面の配色は共通スタイルに合わせる」よりも、「権限の一覧では、利用中と停止中を文字と色で見分けたい」のように、利用者が必要とする振る舞いを書く。
- 「操作ログは別途検討する」よりも、「監査担当者は、誰がいつ権限を変更したかを過去1年分確認したい」のように、利用者と目的を具体化する。
- 「別紙を参照」「詳細は後日」「今回の図には含めない」だけで対象外と判断できる文章を避ける。
- 全問共通の無関係なノイズを大量に流用せず、その問題の背景と整合させる。

画面仕様や監査要件そのものを不要と教えない。「要求として必要か」と「今回の処理フロー図の要素になるか」を区別する。監査ログの記録処理などを図に含めるべき問題では、同じ話題を対象外にしない。

## 左側にもゴミ箱を設ける

- 左側のボード専用のゴミ箱を設け、右側の解答カード用ゴミ箱と独立させる。
- 各付箋の「×」から移動できるようにし、ゴミ箱には枚数を表示する。ゴミ箱内では本文を確認し、「戻す」で復元できるようにする。
- ゴミ箱へ移す対象は開示済みの資料付箋とする。追加資料を開くための付箋は対象にしない。
- 復元時は元の位置を優先する。追加された付箋との重なりなどで置けない場合は、近くの空き位置に置く。
- 付箋の整理によって右側のカード・接続・正誤判定を変更しない。必要なメモを捨てても、それだけでは減点しない。
- 一度開示した資料は、捨てても未開示に戻さない。復元による再減点は行わず、開示済み枚数と減点を保持する。
- 再挑戦・問題切り替えでは、左側の位置・ゴミ箱・開示状態を初期化する。解答確定後は右側と同様に削除・復元・移動を止める。
- 削除・復元はキーボードでも操作でき、ボタンの操作が付箋のドラッグとして扱われないようにする。

## 段階開示と難易度

追加資料を1枚ずつランダムに開示し、1枚につき1点減点する既存の仕組みは、今回の調整では維持する。必要な根拠が未開示の場合は、追加資料で確認する前提とする。

初期付箋の構成は「概要1枚＋対象外2枚」という内部種別の固定から見直し、業務の背景や基本的な事実から着手できる3枚を問題ごとに選ぶ。初期付箋にも判断の根拠を含めてよい。全資料を確認すれば、追加の業務知識を仮定せずに必要な要素と接続を判断できるようにする。

- 初級：担当・前提が明確で、少ないメモの照合で流れを決められる。
- 中級：複数のメモに分かれた条件や役割を合わせて判断する。
- 上級：分岐・やり直し・並行処理などを含み、条件と結果を照合する。

難易度は曖昧さや無関係な情報の量で上げない。不可欠な資料の開示でも減点される既存方式の妥当性は、今回の文章調整とは別の検討事項とする。

## データと生成処理の調整

1. `documents-source.json` に問題ごとの要求仕様と手書きのメモ本文を管理する。`problems.json` だけの直接修正で終わらせず、再生成しても内容が戻らない構成にする。
2. `build-documents.mjs` の正解接続から本文を自動生成する方式を見直す。本文は業務の意味に基づいて作成し、スクリプトは組み立て・ID管理・検証を担当する。設計工程の種別もランダムに割り当てない。
3. `covers` は根拠を追跡する内部情報として使う。初期・追加の両方を検証対象にし、全接続の根拠を確認する。1接続につき1枚という制約は外し、複数枚で根拠を補えるようにする。
4. 対象外の文章に必要カードのラベルが含まれるだけでエラーにする検証は見直す。話題が重なっていても対象範囲の違いで判断できるかをレビューする。
5. `connectionAlternatives` を持つ問題は許容する接続にも根拠があるか確認する。文章から別の妥当な解釈が生じる場合は、文章か正解データを調整する。
6. レビュー資料の生成処理と関連READMEを新しい役割・表示・検証方針に合わせる。

`covers` が埋まっていることだけでは文章の妥当性を保証できない。必要なカードの選択理由、各接続、分岐条件、対象外にする理由を人が読んで確認する。

## 実施順序

1. `access-request` を代表問題として、要求仕様・付箋本文・対象外情報を一式作成し、解答との整合を確認する。
2. 分岐・やり直し・並行処理のある問題でも文章の粒度を確認する。
3. 上部の表示変更、付箋見出しの削除、色の扱いの変更、左側ゴミ箱を実装する。
4. 生成処理と検証を更新し、残りの問題へ展開する。
5. レビュー資料と関連仕様を再生成・更新し、配信用の `docs/organize-drill` にもプロジェクトの配信手順で反映する。

## 完了時の確認事項

- 上部だけで依頼の目的と今回図にする範囲が分かる。
- 左側の付箋に分類見出しがなく、本文と範囲を読んで必要性を判断できる。
- 正解カードのラベルを順番に転記しただけの付箋構成になっていない。
- 対象外の付箋も具体的な要求であり、対象外にする理由を説明できる。
- 全資料から正解の根拠を説明でき、書かれていない前提を学習者に要求しない。
- 左右のゴミ箱が独立し、左側で削除・復元しても右側の解答と開示減点が変化しない。
- 追加開示、位置の復元、キーボード操作、再挑戦、問題切り替え、解答確定後の状態を確認する。
- データ再生成後も要求仕様と調整したメモが保持される。
