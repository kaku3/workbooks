# サービス更新の流れを整理する

- 問題ID：`release-flow`
- 直接開く：`src/index.html?drill=release-flow`
- 難易度：easy
- 出典：`src/data/problems.json`

## 要求仕様

サービス更新を安全に公開し、公開後に利用できることまで確認したい。 今回の図の対象：サービスの更新を、準備から本番への公開、公開後の確認まで安全に進める流れを見直す。

### 操作

要求仕様と左側のメモを読み、右側のカードで必要な処理と関係を図にしてください。

## 段階開示資料

左側にはヒアリングメモを本文だけの付箋で表示します。最初は3枚で、判断の根拠も含みます。「（他のメモも見る）」で追加メモをランダムに1枚開示し、1点減点します。付箋は移動・ゴミ箱への整理・復元ができます。復元による再減点はありません。以下の種別と正解接続はレビュー用の内部情報です。

### 最初に表示する3枚

1. テストには今回の更新内容と公開手順を使う。準備できていない更新は検証対象にしない。（内部種別：要件・要求／根拠：更新内容と公開手順を準備する → テストを実行する）
2. 公開を判断する人には、更新内容だけでなくテストの実行結果も渡す。（内部種別：要件・要求／根拠：テストを実行する → 公開の承認を得る）
3. チーム責任者は、運用を担当できる人を増やすため四半期ごとの採用計画を立てたい。（内部種別：スコープ外／根拠：対象外）

## ヒント

公開する前と、公開した後では、確認することが違いそうです。採用計画の付箋は今回の流れに関係するでしょうか？

## 付箋

| ID | 種別 | ラベル |
|---|---|---|
| `prepare-release` | 必要 | 更新内容と公開手順を準備する |
| `run-tests` | 必要 | テストを実行する |
| `approve-release` | 必要 | 公開の承認を得る |
| `deploy-release` | 必要 | 更新を本番環境へ公開する |
| `monitor-release` | 必要 | 公開後の動作を確認する |
| `recruit-staff` | 余分・参考 | チームの採用計画を立てる |

## グループ

- **公開前の準備**：`prepare-release`, `run-tests`, `approve-release`
- **公開後の確認**：`deploy-release`, `monitor-release`

## 正解の接続

- `prepare-release` → `run-tests`
- `run-tests` → `approve-release`
- `approve-release` → `deploy-release`
- `deploy-release` → `monitor-release`

## 正解例の配置

| 付箋ID | x | y |
|---|---:|---:|
| `prepare-release` | 0.12 | 0.5 |

## 解説

更新を準備し、テストと承認を経て公開します。公開した後の動作確認までをつなぐと、更新作業全体が見える図になります。採用計画は別のテーマです。
