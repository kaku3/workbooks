# サービス更新の流れを整理する

- 問題ID：`release-flow`
- 直接開く：`src/index.html?drill=release-flow`
- 難易度：easy
- 出典：`src/data/problems.json`

## 問題文

「サービス更新の流れを整理する」の見直しにあたり、関係者から集めたメモと設計資料です。今回整理する範囲を考えながら、必要な情報を集めてください。

### 課題

資料の順番に惑わされず、必要な付箋を選んで図にしてください。

## 段階開示資料

左側のホワイトボードに付箋として表示します。最初は外部設計1枚＋スコープ外2枚。「（ヒントを見る）」を押すたびに追加資料を1枚開示し、開くたびに1点減点します。追加資料は必要な情報とスコープ外の情報が混ざっており、開示順は毎回ランダムです。付箋はドラッグで自由に動かせます。

### 最初に表示する3枚

1. 外部設計｜処理概要（外部設計）：サービスの更新を、準備から本番への公開、公開後の確認まで安全に進める流れを見直す。
2. 設定メモ（スコープ外）：APIのタイムアウトは設定ファイルで管理する。
3. チームメモ（スコープ外）：チームの採用計画を立てる作業は、四半期ごとに別途行っている。

### 追加で開示する資料（順不同）

| 資料 | 内容 | 種別 | 根拠になる正解接続 |
|---|---|---|---|
| 要求メモ | 「更新内容と公開手順を準備する」の次は「テストを実行する」を行う。 | 要件・要求 | 更新内容と公開手順を準備する → テストを実行する |
| 詳細設計｜内部処理 | 「テストを実行する」を受けて、「公開の承認を得る」につなぐ。 | 詳細設計 | テストを実行する → 公開の承認を得る |
| 外部設計｜処理順序 | 「公開の承認を得る」を行った後に、「更新を本番環境へ公開する」へ進む。 | 外部設計 | 公開の承認を得る → 更新を本番環境へ公開する |
| 外部設計｜処理順序 | 「更新を本番環境へ公開する」を受けて、「公開後の動作を確認する」につなぐ。 | 外部設計 | 更新を本番環境へ公開する → 公開後の動作を確認する |

## ヒント

公開する前と、公開した後では、確認することが違いそうです。採用計画の付箋は今回の流れに関係するでしょうか？

## 付箋

| ID | 種別 | ラベル |
|---|---|---|
| `prepare-release` | 必要 | 更新内容と公開手順を準備する |
| `run-tests` | 必要 | テストを実行する |
| `approve-release` | 必要 | 公開の承認を得る |
| `deploy-release` | 必要 | 更新を本番環境へ公開する |
| `monitor-release` | 必要 | 公開後の動作を確認する |
| `recruit-staff` | 余分・参考 | チームの採用計画を立てる |

## グループ

- **公開前の準備**：`prepare-release`, `run-tests`, `approve-release`
- **公開後の確認**：`deploy-release`, `monitor-release`

## 正解の接続

- `prepare-release` → `run-tests`
- `run-tests` → `approve-release`
- `approve-release` → `deploy-release`
- `deploy-release` → `monitor-release`

## 正解例の配置

| 付箋ID | x | y |
|---|---:|---:|
| `prepare-release` | 0.12 | 0.5 |
| `run-tests` | 0.31 | 0.5 |
| `approve-release` | 0.5 | 0.5 |
| `deploy-release` | 0.69 | 0.5 |
| `monitor-release` | 0.88 | 0.5 |

## 解説

更新を準備し、テストと承認を経て公開します。公開した後の動作確認までをつなぐと、更新作業全体が見える図になります。採用計画は別のテーマです。
