# 問い合わせ対応を整理する

- 問題ID：`support-flow`
- 直接開く：`src/index.html?drill=support-flow`
- 難易度：easy
- 出典：`src/data/problems.json`

## 問題文

「問い合わせ対応を整理する」の見直しにあたり、関係者から集めたメモと設計資料です。今回整理する範囲を考えながら、必要な情報を集めてください。

### 課題

図に載せる情報を見極め、付箋を矢印でつないでください。

## 段階開示資料

左側のホワイトボードに付箋として表示します。最初は外部設計1枚＋スコープ外2枚。「（ヒントを見る）」を押すたびに追加資料を1枚開示し、開くたびに1点減点します。追加資料は必要な情報とスコープ外の情報が混ざっており、開示順は毎回ランダムです。付箋はドラッグで自由に動かせます。

### 最初に表示する3枚

1. 外部設計｜処理概要（外部設計）：利用者から不具合の報告を受けてから、対応結果を伝えるまでの問い合わせ対応を見直す。
2. 運営メモ（スコープ外）：翌月の研修計画を作る作業は、サポートチームの別の会議で進めている。
3. 要求メモ（スコープ外）：画面の雰囲気は現行システムに近づけたい。

### 追加で開示する資料（順不同）

| 資料 | 内容 | 種別 | 根拠になる正解接続 |
|---|---|---|---|
| 外部設計｜処理順序 | 「利用者が不具合を報告する」を受けて、「担当者が発生条件を確認する」につなぐ。 | 外部設計 | 利用者が不具合を報告する → 担当者が発生条件を確認する |
| 詳細設計｜内部処理 | 「担当者が発生条件を確認する」が終わったら、「原因を切り分ける」に移る。 | 詳細設計 | 担当者が発生条件を確認する → 原因を切り分ける |
| 外部設計｜処理順序 | 「原因を切り分ける」を行った後に、「修正または回避策を行う」へ進む。 | 外部設計 | 原因を切り分ける → 修正または回避策を行う |
| 外部設計｜処理順序 | 「修正または回避策を行う」の次は「結果を利用者へ共有する」を行う。 | 外部設計 | 修正または回避策を行う → 結果を利用者へ共有する |
| 要求メモ | 導入時期は繁忙期を避けたい。 | スコープ外 | —（図に含めない） |
| 開発標準メモ | 保存先テーブル名は開発標準に従う。 | スコープ外 | —（図に含めない） |

## ヒント

利用者への返答だけでなく、その前に状況を確かめる作業にも目を向けてみましょう。

## 付箋

| ID | 種別 | ラベル |
|---|---|---|
| `report-issue` | 必要 | 利用者が不具合を報告する |
| `confirm-context` | 必要 | 担当者が発生条件を確認する |
| `isolate-cause` | 必要 | 原因を切り分ける |
| `apply-fix` | 必要 | 修正または回避策を行う |
| `share-result` | 必要 | 結果を利用者へ共有する |
| `plan-training` | 余分・参考 | 翌月の研修計画を作る |

## グループ

- **問い合わせの受付**：`report-issue`, `confirm-context`
- **原因の調査と対処**：`isolate-cause`, `apply-fix`

## 正解の接続

- `report-issue` → `confirm-context`
- `confirm-context` → `isolate-cause`
- `isolate-cause` → `apply-fix`
- `apply-fix` → `share-result`

## 正解例の配置

| `report-issue` | 0.12 | 0.5 |

## 解説

問い合わせの内容を把握して発生条件を確かめ、原因を切り分けて対処します。対応した結果を利用者へ共有して一連の流れが完了します。研修計画は問い合わせ対応とは別の業務です。
