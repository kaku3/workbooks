# 図解ドリル — 実装・運用メモ

## 1. 目的と設計方針

「頭ではわかっているのに、相手に伝わらない」を出発点に、自分の理解を、相手が判断できる形の図に組み立てる練習サイト。要求仕様をAIに丸投げして出来た図をレビューし、伝えるべき主題を見つけ、概要文と修正版の図（draw.io）を自分で作る。単に「正しい図」を当てるのではなく、情報の優先順位、主題、関係性、読み順を自分で考えることを目的とする。

サイトの訴求は、ヒーローの eyebrow・見出し・リード文と、導入パネルの文章（`intro-copy`）で示している。要点は「相手が知りたいのは頭の中のすべてではなく、何を決めるのか・そのために何が要るのか」「図なら、描きながら順番や抜けを確かめられ、自分の理解も固まる」「開発全般で必要になる説明力を鍛える」の3点。メタタグ・OGP（§2.1）もこの訴求に合わせる。

教材の基本方針は次のとおり。

- **悪い例も、良い例と同じ形式・同じ題材で比較できること。**
- 悪い例は、明らかな誤図や奇抜な図ではなく、内容はおおむね正しそうだが、主題・関係・読み順が少し分かりにくい「惜しい図」にする。
- 良い例は、装飾を増やすのではなく、情報の構造と視線の流れを整えて改善する。
- 1問につき学習ポイントを絞り、設問を進めるにつれてプレゼン資料の基本を少しずつ学べるようにする。
- 図の美しさだけでなく、「読み手が何を理解し、どんな判断をできるか」を評価する。

参考: [プレゼンレイアウトのコツ6選 — good presen!](https://goodpresen.jp/journal/slide_layout_selection/)
この記事で扱われる視線の流れ、強調のメリハリ、余白、関連情報のグルーピング、整列、レイアウトの統一感は、本ドリルの図づくりにも応用できる。ただし、図解ドリルでは一般的なスライド装飾の練習ではなく、要求や業務情報の構造化に置き換えて扱う。

## 2. 現在の構成

静的な HTML / CSS / JavaScript で動作し、ビルド工程やサーバー側処理を必要としない。問題定義は JSON、図は PNG 画像として管理する。

```text
20_zukai-drill/
├── docs/
│   ├── ReadMe.md
│   └── lessons.md
└── src/
    ├── index.html
    ├── styles.css
    ├── app.js
    ├── assets/
    │   ├── hero.png
    │   ├── intro.png
    │   └── ogp.png
    └── data/
        ├── problems.json
        └── diagrams/
            ├── <problem-id>_bad-diagram.drawio.png
            └── <problem-id>_good-diagram.drawio.png
```

`*.drawio.png` は draw.io から出力した図画像。拡張子に `drawio` が含まれるが、実行時に SVG を生成しているわけではない。`app.js` が問題 ID から対応する PNG を参照する。画面上では、`_bad-diagram` が「AIが描いた図」、`_good-diagram` が「図 : 修正例」として表示される。

| ファイル | 用途 |
|---|---|
| `assets/hero.png` | ヒーロー領域の背景（`styles.css` から参照） |
| `assets/intro.png` | 導入パネル右側のビジュアル（`index.html` の `intro-visual`） |
| `assets/ogp.png` | SNS シェア用の OGP / Twitter カード画像（1734 × 907、PNG） |

### 2.1 メタタグ・OGP（`index.html` の `<head>`）

`<title>`、`description`、`og:title`、`og:description`、`twitter:title`、`twitter:description` は、ヒーロー（eyebrow・見出し・リード文）と導入文の訴求に合わせた同一の文言を使う。現行の内容は次のとおり。

| 項目 | 内容 |
|---|---|
| title / og:title / twitter:title | 図解ドリル \| 自分の理解を、相手が判断できる図にする練習 |
| description / og:description / twitter:description | 頭ではわかっているのに、相手に伝わらない。AIが描いた図をレビューして主題を見つけ、概要文と修正版の図をつくる全10問のドリル。開発全般で必要な説明力を鍛えます。 |
| og:type / og:site_name / og:locale | `website` / 図解ドリル / `ja_JP` |
| og:url / canonical | `https://kaku3.github.io/workbooks/zukai-drill/` |
| og:image / twitter:image | `https://kaku3.github.io/workbooks/zukai-drill/assets/ogp.png`（絶対 URL。`og:image:type` / `width` / `height` も指定） |
| og:image:alt / twitter:image:alt | OGP 画像内のコピー（「頭では分かっているのに、うまく伝えられない。見つけて、考えて、描いてみる。」）と絵の内容 |
| twitter:card | `summary_large_image` |

更新時のルール。

- ヒーロー・導入文・学習フロー・問題数を変えたら、メタタグの文言も合わせて見直す（以前の「外部設計向け」のような、現状と合わない限定を残さない）。
- 上記の title / description 系は同じ文言を複数箇所に書いているため、片方だけ直さず、まとめて更新する。
- `ogp.png` を差し替えて寸法が変わったら、`og:image:width` / `og:image:height` と alt も更新する。SNS 側のキャッシュは、公開後に各サービスのデバッガーで再取得する。
- 画像 URL は公開 URL（`https://kaku3.github.io/workbooks/zukai-drill/...`）を絶対指定する。相対パスにしない。

## 3. 画面と学習フロー

### 3.1 全体画面

- ヒーロー領域：eyebrow（`ZUKAI DESIGN TRAINING`）、見出し「頭ではわかっているのに、相手に伝わらない。」、リード文（自分の理解を図にして、相手が判断できる形に組み立てる、開発全般で必要になる説明力を鍛えるドリル）で、図解を学ぶ目的を提示する。
- 導入パネル：`intro-copy` で、説明しているつもりでも判断・合意をもらう場面では相手が決められる順番に組み直す必要があること、図なら描きながら確かめられることを示す。右側に `intro.png`。
- 「はじめる」ボタン：前回開いていた問題があればそこから、なければ最初の問題から開始する（最後に開いた問題の位置は `localStorage` に保存）。
- 左の設問メニュー：問題を自由に選択でき、完了した問題に ✓ を表示する。完了数（`完了 n / 10`）と進捗表示で学習状況を確認できる。
- 問題は `problems.json` の配列順に表示し、「前の問題」「次の問題」で移動できる。

### 3.2 問題の画面（全10問共通のレビュー形式）

現行は、全10問が `index.html` の `review-template` を使う同一のレビュー形式で表示される。1画面に「問題（レビュー）」と「問題（作成）」の2段階がある。

**問題（レビュー）**

1. 「要求仕様」を読む（タイプライター表示のあと、「AIが描いた図」が描き込み表示される）。図はタップすると原寸で開く。
2. 「分かりづらいと感じる点」を自分の言葉で入力する（ヒントは `review.lead` の「特に、…」から生成）。
3. 「主題となる点」を選択肢から選ぶ（`tasks.focusOptions`。選ぶ個数は `isCore: true` の数）。
4. 「答えを見る」で、レビューの解答（分かりづらい点の例、主題と主題でないもの、主題の選択結果、図で表すべきポイント）を確認する。

**問題（作成）**

5. 主題として選んだものを材料に、概要文（1〜2文）を入力し、draw.io で修正版の図を作成する。
6. 「答えを見る」で、作成の解答（要約例と見るところ、「図 : 修正例」とその改善点）を確認する。
7. 必要に応じて、「要約を、AIに見てもらう（任意）」から、要約文入りの AI 採点用プロンプトをコピーする。

`tasks.focusOptions[].isCore` は主題に含めるべき情報かどうかを表す。選択結果は「主題 n つのうち m つを選べました」と表示するだけで、完了条件には使わない。情報の取捨選択を意識させるための補助表示。

## 4. 問題データの構造

ルートは `version` と `problems[]`。`problems[]` の各要素は、画面が実際に読む次の項目だけを持つ。

- `id`: 図ファイル名にも使う一意 ID
- `title` / `difficultyLabel`: 設問メニューと問題見出しの表示
- `scenario`: 「要求仕様」として表示する課題文章
- `tasks.focusOptions[]`: 主題の選択候補。`id`、`label`、`isCore`、補足の `note`（主題でない理由。解答欄に表示）を持つ
- `review`: 画面文言と解答の本体
  - `lead`: 共通問題文＋「特に、…」の注目点（ヒントの生成にも使う）
  - `figureAlt`: 「AIが描いた図」の代替テキスト
  - `findingsPlaceholder`: 気づき入力欄の placeholder
  - `keepLead`: 主題選択の案内文
  - `copyLead` / `copyPlaceholder`: 概要文入力欄の案内文と placeholder
  - `findings[]`: 分かりづらい点の解答（`title`、`why`）
  - `fixedAlt` / `fixedNote` / `fixedPoints[]`: 修正例の図の代替テキスト・説明・改善点（いずれも任意。現在は Lesson 4・7・9・10 が未設定で、修正例の図のみ表示される）
  - `copyExample` / `copyPoints[]`: 要約例と、要約で見るところ
  - `transferTip`: 図で表すべきポイント（実務への転用）

「要求仕様」「AIが描いた図」「分かりづらいと感じる点」「図 : 修正例」などの見出しは `index.html` に固定で書かれており、JSON では変更しない。画面に出さない学習目標・図のタイプは JSON に持たず、`lessons.md` で管理する。

図の実体は常に `src/data/diagrams/<id>_bad-diagram.drawio.png` と `..._good-diagram.drawio.png`。問題文、選択肢、解説を更新するときは、JSON の記述と図画像の内容が一致しているかを確認する。図を差し替える場合はファイル名を変えず、PNG と JSON の両方を確認する。

## 5. 図を作るときの品質基準

### 悪い例

- 良い例と同じ題材・同じ種類の図で比較できる。
- 一見すると意味は通るが、読み手が一瞬迷う程度の問題を持つ。
- 問題点は主題、情報の優先順位、関係性、読み順、強調、グルーピング、余白、整列など、学習目標に結びついている。
- 間違った業務仕様や事実を混ぜて「悪さ」を作らない。
- 余計な情報を足すだけでなく、正しい情報の配置や結び方を少し変えることで分かりにくさを作る。

### 良い例

- 悪い例と同じ情報・同じ図の形式を基本にし、構造の改善が比較できる。
- 最初に伝えるべき主題が分かり、視線が自然に流れる。
- 主情報と補足情報に強弱があり、関連する要素は近くにまとめる。
- 余白と整列を保ち、意味のない装飾や色分けを増やさない。
- 良くした理由を、見た目の好みではなく読み手の理解しやすさで説明できる。

### 作成・レビュー時のチェック

1. 読み手は最初に何を理解すべきか。
2. 図の主張は一つに絞れているか。
3. 情報同士の関係（順序、分岐、比較、原因と対策、責務）が明示されているか。
4. 視線の流れは自然か。読み手が行き来して解釈しなくてよいか。
5. 重要度の強弱、グルーピング、余白、整列に一貫性があるか。
6. 悪い例と良い例の差は、学習者が自分で発見できる程度に具体的か。
7. 改善点が `lessons.md` の学習目標と対応しているか。

## 6. 進捗保存と完了条件

ブラウザーの `localStorage` に進捗を保存し、同じブラウザーで再訪したときに復元する。

- 保存キー: `zukai-drill-progress-v1`
- 問題ごとの主題の選択、気づき（`findings`）、概要文（`summary`）、レビュー解答・作成解答の表示状態（`revealedReview` / `revealedCreate`）を保存
- 最後に開いた問題の位置と、選択肢の並び順（問題ごと）も保存し、再訪時に「はじめる」で続きから始められる／並びが不用意に変わらないようにする
- 保存データがない場合や復元に失敗した場合は、初期状態から開始する

問題の完了条件は、次の4つをすべて満たすこと。満たすと設問メニューに ✓ が付く。

1. 「分かりづらいと感じる点」に入力がある
2. 概要文（要約）に入力がある
3. レビューの解答を表示した
4. 作成の解答を表示した

主題の選択結果（何個選べたか）は、完了条件には含めない。以前のバージョンが保存した項目（自己採点の状態など）が `localStorage` に残っていても、読み込み時に無視される。

## 7. 実装・更新時の注意

- 問題の追加・順序変更は `src/data/problems.json` で行う。新しい問題にも `review` オブジェクトを必ず持たせる（持たない問題は、現行の画面では表示できない）。
- 問題数を変えたら、メタタグの「全10問」、`lessons.md` の全問一覧もそろえる。
- 使わなくなったフィールド・コード・CSS は残さず削除する（参照されない項目を JSON に置かない）。
- 図画像の参照先は問題 ID に依存する。IDを変更する場合は図ファイル名もそろえる。
- 「AIが描いた図」（`_bad-diagram`）と「図 : 修正例」（`_good-diagram`）の見出し・解説と、実際の PNG の内容を必ず一致させる。
- ヒーロー・導入文・学習フローを変更したら、`index.html` のメタタグ・OGP（§2.1）も更新する。
- `lessons.md` は `problems.json` の内容を Lesson 別にまとめた資料で、学習目標と図のタイプも持つ。`problems.json` を更新したら `lessons.md` も合わせる。実装の仕様説明は本書に書く。
- UIや保存仕様を変更した場合は、この文書も更新する。
