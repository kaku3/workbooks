# 図解ドリル — 実装・運用メモ

## 1. 目的と設計方針

要求仕様の文章から、伝えるべき情報を選び、関係や順序を整理して、読み手が短時間で理解できる図にする練習サイト。単に「正しい図」を当てるのではなく、情報の優先順位、主題、関係性、読み順を自分で考えることを目的とする。

教材の基本方針は次のとおり。

- **悪い例も、良い例と同じ形式・同じ題材で比較できること。**
- 悪い例は、明らかな誤図や奇抜な図ではなく、内容はおおむね正しそうだが、主題・関係・読み順が少し分かりにくい「惜しい図」にする。
- 良い例は、装飾を増やすのではなく、情報の構造と視線の流れを整えて改善する。
- 1問につき学習ポイントを絞り、設問を進めるにつれてプレゼン資料の基本を少しずつ学べるようにする。
- 図の美しさだけでなく、「読み手が何を理解し、どんな判断をできるか」を評価する。

参考: [プレゼンレイアウトのコツ6選 — good presen!](https://goodpresen.jp/journal/slide_layout_selection/)
この記事で扱われる視線の流れ、強調のメリハリ、余白、関連情報のグルーピング、整列、レイアウトの統一感は、本ドリルの図づくりにも応用できる。ただし、図解ドリルでは一般的なスライド装飾の練習ではなく、要求や業務情報の構造化に置き換えて扱う。

## 2. 現在の構成

静的な HTML / CSS / JavaScript で動作し、ビルド工程やサーバー側処理を必要としない。問題定義は JSON、図は PNG 画像として管理する。

```text
20_zukai-drill/
├── docs/
│   ├── ReadMe.md
│   └── lessons.md
└── src/
    ├── index.html
    ├── styles.css
    ├── app.js
    ├── assets/
    │   ├── hero.png
    │   ├── intro.png
    │   └── ogp.png
    └── data/
        ├── problems.json
        └── diagrams/
            ├── <problem-id>_bad-diagram.drawio.png
            └── <problem-id>_good-diagram.drawio.png
```

`*.drawio.png` は draw.io から出力した図画像。拡張子に `drawio` が含まれるが、実行時に SVG を生成しているわけではない。`app.js` が問題 ID から対応する PNG を参照する。

## 3. 画面と学習フロー

### 3.1 全体画面

- ヒーロー領域で、図解を学ぶ目的を提示する。
- 設問ナビゲーションから問題を選択できる。
- 完了数と進捗表示で学習状況を確認できる。
- 問題は `problems.json` の配列順に表示する。

### 3.2 作成型問題（lesson 3 以降の現行形式）

1. 課題文章を読む。
2. 図の主役にする情報を選択肢から選び、自己採点する。
3. 1〜2文で主題を要約する。
4. 解答を開き、悪い図の問題点、良い図、改善原則、実務への転用ポイントを確認する。
5. 必要に応じて、要約文を含む AI 採点用プロンプトをコピーする。

`tasks.focusOptions[].isCore` は主情報かどうかを表す。得点は選択した主情報に加点し、補足情報の選択には減点する自己採点方式。これは知識試験の正答率というより、情報の取捨選択を意識させるための補助機能。

### 3.3 レビュー型問題（lesson 1・2）

1. 要求仕様を読む。
2. AI作成版の図を見て、分かりづらい点を自分の言葉で記述する。
3. 図に残すべき主情報を選ぶ。
4. 改善例と解説を確認する。
5. 改善例を踏まえて、主題を伝える短いコピー／説明文を作成する。

レビュー型は「正解の図を描く」前に、違和感を見つけて言語化する練習を行う構成。`problems.json` の `review` オブジェクトが画面文言、図の説明、改善例、コピー作成の情報を持つ。

## 4. 問題データの構造

ルートは `version`、`meta`、`problems[]`。

共通項目:
- `id`: 図ファイル名にも使う一意 ID
- `title`: 設問タイトル
- `difficultyLabel`: 表示する難易度
- `learningGoal`: 学習目標
- `scenario`: 課題文章
- `tasks.focusOptions[]`: 主情報選択の候補。`id`、`label`、`isCore` を持つ

作成型問題:
- `badDiagram.title` / `badDiagram.mistakes[]`: 悪い例の見出しと、改善前に気づきたい点
- `goodDiagram.title` / `goodDiagram.principles[]`: 良い例の見出しと、図づくりの原則
- `transferTip`: 実務への転用ポイント
- 図の実体は `src/data/diagrams/<id>_bad-diagram.drawio.png` と `..._good-diagram.drawio.png`

レビュー型問題:
- `review`: 導入文、仕様注記、図の説明、気づき欄、改善例、コピー作成欄、解説など
- 図画像は同じ命名規則で `bad` / `good` を用意する

問題文、選択肢、解説を更新するときは、JSONの記述と図画像の内容が一致しているかを確認する。図を差し替える場合はファイル名を変えず、PNGとJSONの両方を確認する。

## 5. 図を作るときの品質基準

### 悪い例

- 良い例と同じ題材・同じ種類の図で比較できる。
- 一見すると意味は通るが、読み手が一瞬迷う程度の問題を持つ。
- 問題点は主題、情報の優先順位、関係性、読み順、強調、グルーピング、余白、整列など、学習目標に結びついている。
- 間違った業務仕様や事実を混ぜて「悪さ」を作らない。
- 余計な情報を足すだけでなく、正しい情報の配置や結び方を少し変えることで分かりにくさを作る。

### 良い例

- 悪い例と同じ情報・同じ図の形式を基本にし、構造の改善が比較できる。
- 最初に伝えるべき主題が分かり、視線が自然に流れる。
- 主情報と補足情報に強弱があり、関連する要素は近くにまとめる。
- 余白と整列を保ち、意味のない装飾や色分けを増やさない。
- 良くした理由を、見た目の好みではなく読み手の理解しやすさで説明できる。

### 作成・レビュー時のチェック

1. 読み手は最初に何を理解すべきか。
2. 図の主張は一つに絞れているか。
3. 情報同士の関係（順序、分岐、比較、原因と対策、責務）が明示されているか。
4. 視線の流れは自然か。読み手が行き来して解釈しなくてよいか。
5. 重要度の強弱、グルーピング、余白、整列に一貫性があるか。
6. 悪い例と良い例の差は、学習者が自分で発見できる程度に具体的か。
7. 改善点が `lessons.md` の学習目標と対応しているか。

## 6. 進捗保存と完了条件

ブラウザーの `localStorage` に進捗を保存し、同じブラウザーで再訪したときに復元する。

- 保存キー: `zukai-drill-progress-v1`
- 問題ごとの選択、自己採点状態、入力文、解答表示状態、レビューの気づきなどを保存
- 選択肢の並び順も問題ごとに保存し、再訪時に不用意に変わらないようにする
- 保存データがない場合や復元に失敗した場合は、初期状態から開始する

作成型問題は、主情報をすべて選択したうえで自己採点し、要約文を入力して解答を表示すると完了扱いになる。レビュー型問題は、気づきとコピーの入力があり、レビュー解答と作成解答の両方を表示すると完了扱いになる。

## 7. 実装・更新時の注意

- 問題の追加・順序変更は `src/data/problems.json` で行う。
- 図画像の参照先は問題 ID に依存する。IDを変更する場合は図ファイル名もそろえる。
- `badDiagram` / `goodDiagram` の見出し・解説と、実際の PNG の内容を必ず一致させる。
- `lessons.md` は教材設計の意図・各問の学習ポイント・未解決事項を管理する。実装済みの仕様説明は本書、教材として何を学ばせるかは `lessons.md` に分ける。
- UIや保存仕様を変更した場合は、この文書も更新する。
