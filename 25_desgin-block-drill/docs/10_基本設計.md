# 設計ブロックドリル — 基本設計

## システム概要

ブラウザで動く小規模な決定的シミュレーター。自由なプログラミング環境ではなく、問題定義に含まれるデータ・処理・条件を組み合わせる。アニメーションと実行エンジンを分離する。

## 画面

### 左：テストケース

ケースの説明、初期条件、個別実行、実行結果、ケースごとの成功・失敗を表示する。「独立したテストの一括実行」と「共有状態を持つ複数イベントのシナリオ」を区別する。

### 上：実行操作

Play / Pause / Step / Reset、実行速度、ステップ番号、実行中・待機・停止・完了の状態。

### 中央：キャンバス

処理ブロックを接続し、成功・失敗の出力先を設定する。荷物は線に沿って移動する。ブロック内では候補の操作カードを選択・並べ替えできる。待機中の荷物はキューに並び、詰まった箇所を見えるようにする。

### 詳細とログ

荷物選択時にID、位置、注文状態、引当数量、決済状態、キャンセル状態、出荷状態、直近の実行結果を表示する。ブロック選択時には入力条件、操作列、成功／失敗経路を表示する。ログにはステップ、荷物ID、操作、結果、状態差分、遷移先を記録する。

## データモデル（初期案）

### 注文／荷物

| 項目 | 値の例 | 意味 |
|---|---|---|
| orderId | ORD-001 | 注文ID |
| itemId | ITEM-A | 商品ID |
| quantity | 2 | 注文数量 |
| orderStatus | accepted / cancelled / completed | 注文状態 |
| reservationStatus | none / reserved / released | 在庫引当状態 |
| reservedQuantity | 0, 2 | 実際の引当数量 |
| paymentStatus | pending / paid / failed / refunded | 決済状態 |
| shippingStatus | none / requested / shipped | 出荷状態 |
| cancellationStatus | none / requested / succeeded / failed | キャンセル状態 |

### 共有状態

商品別在庫数、注文の処理履歴、通知履歴、必要に応じた処理中ロック。注文単位のデータと共有データを明確に区別する。

## 処理ブロック

各ブロックは入力条件、操作列、成功時の遷移先、失敗時の遷移先、待機条件、出力イベントを持つ。操作結果は `success` / `failure` / `wait` / `no_op` を基本とする。

- **失敗**：条件を満たさない。状態を勝手に成功扱いにしない。
- **待機**：条件が整うまで荷物が止まる。後続荷物の滞留を表示する。
- **停止**：遷移先なし、上限到達など、設計上の行き止まり。

## 初期題材：注文・在庫・決済・出荷・キャンセル

候補操作は、注文受付、在庫引当、決済、出荷指示、キャンセル要求、在庫引当解除、返金、キャンセル確定、通知。

基本ルール：

- 在庫引当は在庫が足りる場合だけ成功し、引当数量を記録する。
- 在庫引当解除は、当該注文の引当記録がある場合だけ成功する。
- 返金は決済済みの注文に対してだけ成立する。
- 出荷指示は有効な注文で、必要な引当・決済条件が成立した場合だけ作れる。
- キャンセル完了通知は、キャンセル成功が確定した場合だけ送るのが期待仕様。
- 出荷済みなどキャンセルできない状態では、完了通知を送らない。

教材上は、通知ブロックが成功確認なしで送信するように組める。その場合、**失敗後の誤通知が実際に発生する**。問題エンジンは不正な設計もそのまま実行し、判定器が副作用を検出する。

## 実行モード

- **個別テスト**：毎回初期状態から開始。前のテストの在庫・通知を引き継がない。
- **一括テスト**：独立ケースをそれぞれリセットして実行し、結果を集約。
- **複合シナリオ**：1ケース内で複数イベントを投入し、在庫などの共有状態を引き継ぐ。

## 初期版の対象外

外部メール送信、実決済、任意JavaScript、DB設計、分散トランザクション、厳密な並列処理。通知はシミュレーション内のイベント履歴として扱う。
