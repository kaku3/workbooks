# 総合：権限・承認・振込の整合性

ID：`approval-system`／第2章ステージ4。[共通仕様](02-00_approval-rules.md)。

## 出題・初期設計

経費精算の受入試験です。承認者の権限、差戻し、再申請、処理の再実行を含め、全ケースで整合する設計へ修正してください。

判断入口はrecordDecisionだけで現版承認確認へ接続。経理入口も現版承認確認へ接続。現版承認確認→経理（verifyReceipt）→振込（transfer）→通知（sendPaid）。承認確認の失敗先は通知、経理失敗は完了、振込失敗も通知。再申請入口はreviseRequestで完了。

パレットには振込済み確認（paymentCompleted）、差戻し（returnRequest）を各1個。承認者確認（checkApprover）は判断入口へのカード追加で組み込む。カード候補は共通仕様の全操作。

## テスト集合

初級AP-01・02、中級AR-01・02・04と総合専用の上長差戻しAR-03、上級AT-01〜05をそれぞれ独立した初期状態で再実行する。IDが違っても同じ入力のAR-01/AP-01は受入観点別の重複として維持し、集計は13ケース。追加の2件は次のとおり。

| ID | 初期状態・入力 | 期待 |
|---|---|---|
| AS-01 | R-01・1,200円・版1・pending/unpaid、申請者E-01、actor=E-02（employee）でapprove | 判断記録前に拒否。pending、承認版null、振込0・通知0 |
| AS-02 | 同上、actor=E-01（employeeとmanager）でapprove | 上長権限があっても本人承認を拒否。同じ期待 |

各テストは最後に全荷物の正常終了を求める。権限拒否のfailureを(完了)へ送ること自体は合格で、権限違反の判断記録や振込を行わない。

## 作者向け修正例

判断入口でcheckApproverを先に行う。経理前にpaymentCompletedで再実行を除外し、現版承認確認→verifyReceipt→transfer→sendPaid。verifyReceipt失敗はreturnRequest→完了、承認・振込失敗は完了。再申請の版更新を維持する。

同じ処理をブロック分割しても、一つのブロックに安全な順でまとめてもよい。権限チェックを判断記録の後に置いた場合は、最終的に振り込まなくてもAS-01・02の承認状態で失敗する。
