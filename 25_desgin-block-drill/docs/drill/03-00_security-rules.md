# 第3章共通仕様：認証・セッション・権限

状態：実装済み。値・入力・期待値の実装契約。ゲーム内の抽象モデルであり、本番の認証システムの実装手順を示すものではない。

## 公開するルール

- ログインは、未ロック・パスワード一致・追加認証一致のすべてが必要。
- 照合失敗は1入力につき1回だけ加算する。パスワードと追加認証が両方不一致でも2回にはしない。
- 連続失敗3回でロックする。ロック済みの入力は照合に進めず、失敗回数も増やさない。
- ログイン成功時に失敗回数を0へ戻す。成功以外で回数を消してはいけない。
- 管理機能は、有効な本人のセッションと管理権限の両方が必要。
- ログアウト済み・期限切れ・他人のセッションでは管理機能を実行できない。
- 拒否が期待される入力も処理を終了する。拒否そのものはテスト失敗ではない。

ロックの自動解除、時刻経過によるアンロック、パスワードの実データ、暗号方式、外部通信、並列処理は扱わない。ロック閾値3はゲーム内の固定ルール。

03-01は照合と発行だけの導入とし、回数記録・ロック・成功時リセットの設計は03-02から要求する。03-01のテストは回数を採点せず、初期回数0・未ロックで固定する。総合では全ルールを適用する。

## 状態

| 対象 | フィールド | 意味 |
|---|---|---|
| `users[userId]` | `role` | `member` / `admin` |
| 同上 | `failedCount` | 連続失敗回数。整数0〜3 |
| 同上 | `locked` | ロック済みか |
| `sessions[sessionId]` | `userId` | 発行先ユーザー |
| 同上 | `active` | ログアウトされていないか |
| 同上 | `expiresAt` | 有効期限。整数の仮想時刻 |
| `attempts[inputId]` | `passwordChecked` / `mfaChecked` | この入力で各照合に成功したか。初期false |
| 同上 | `failureRecorded` | この入力の失敗を加算済みか。初期false |
| 同上 | `sessionIssued` | この入力でセッションを発行したか。初期false |
| `effects` | 発生した処理の配列 | 発行・管理処理・失効・監査を発生時点の情報と共に記録 |

初期状態は各ケースに明記する。ユーザーは会員U-01、管理者A-01、別会員U-02。特記しないユーザーは失敗0・未ロック。事前発行セッションは、有効な認証を済ませた既存状態として与える。ケース内の入力はFIFOで処理し、状態を引き継ぐ。ケース間では完全に初期化する。

## 入力

| type | 開始ブロック | 入力値 |
|---|---|---|
| `login` | ログイン受付 | `inputId`, `userId`, `passwordMatches`, `mfaMatches`, `sessionId`, `now`, `expiresAt` |
| `adminAction` | 管理受付 | `inputId`, `actorId`, `sessionId`, `now` |
| `logout` | ログアウト受付 | `inputId`, `actorId`, `sessionId`, `now` |

照合結果はその入力だけの値。別入力で成功した `passwordChecked` / `mfaChecked` を流用しない。`userId` / `actorId` はシミュレーションへの信頼済み入力で、リクエスト本文から本人を証明する課題ではない。`now` は固定データで、実際の時計に依存しない。

セッションIDは入力に与える。発行時に同一IDがすでにあれば失敗し、別ユーザーの既存セッションを上書きしない。03-04ではこの衝突も検証する。

## 処理契約

失敗時は状態を変更しない。各処理は成功／失敗の2分岐。1ブロックに複数の処理がある場合は先頭から実行し、失敗後の残りは実行しない。

| 処理ID・表示名 | 成功条件 | 成功時の変化 | 失敗条件 |
|---|---|---|---|
| `requireUnlocked` ロック状態を確認 | ユーザーが存在し未ロック | 変更なし | 不明ユーザー・ロック済み |
| `checkPassword` パスワードを確認 | login入力でユーザーが存在し、未ロック、一致 | この入力のpasswordChecked=true | 条件不足 |
| `checkMfa` 追加認証を確認 | login入力でユーザーが存在し、未ロック、一致 | この入力のmfaChecked=true | 条件不足 |
| `recordLoginFailure` 失敗回数を記録 | ユーザーが存在し未ロック、この入力の照合結果に少なくとも1つ不一致 | 未加算ならfailedCountを1増加（最大3）、failureRecorded=true。加算済みなら変更なし | ロック済み・両方一致・login以外 |
| `requireFailureLimit` 失敗回数を確認 | failedCount>=3 | 変更なし | 3未満 |
| `lockUser` アカウントをロック | ユーザーが存在しfailedCount>=3 | locked=true | 条件不足 |
| `issueSession` セッションを発行 | login入力、ユーザーあり、未ロック、ID未使用、expiresAt>now | セッションをactive=trueで作成、sessionIssued=true、発行記録1件 | 条件不足・ID衝突 |
| `resetLoginFailures` 失敗回数をリセット | この入力で正しくセッション発行済み | failedCount=0 | 発行なし・不正発行 |
| `requireSession` セッションを確認 | active=true、session.userId=actorId、now<expiresAt | 変更なし | 不存在・失効・他人・期限切れ |
| `requireAdmin` 管理権限を確認 | actorIdのrole=admin | 変更なし | 権限なし・不明ユーザー |
| `runAdminAction` 管理処理を実行 | 管理入力、actorIdが存在 | 管理処理記録1件 | 入力不正 |
| `revokeSession` セッションを失効 | セッションが存在しsession.userId=actorId | active=false、初回だけ失効記録1件。失効済みなら変更なし | 不存在・他人 |
| `recordSecurityAudit` 監査を記録 | 入力が存在 | 入力番号・実行者・種類の履歴1件。認証状態は変えない | なし |

`issueSession` は照合成功のゲートを自動挿入しない。`runAdminAction` もセッション・権限のゲートを自動挿入しない。条件を設計につなぐ教材のため、誤接続時には不正な発行・実行が実際に起き、後述の判定で失敗する。

## 発生時点の検証と累計

- 発行記録には入力ID、ユーザー、セッションID、発行時点のロック・照合確認済みフラグを固定保存する。両照合がこの入力で成功していなければ不正発行。
- 管理処理記録には実行者、セッション、時刻、その時点の本人一致・有効性・管理権限を固定保存する。どれか欠ければ不正実行。
- ログイン成功／失敗は入力データから定義する。結果の帳尻だけでなく、失敗加算・リセット・ロックの入力ごとの発生位置も検証する。
- 失効したIDの再発行・上書きは許可しない。不正発行を後からログアウトしても合格にはならない。
- 「セッション発行の合計」「管理処理の合計」と「不正なセッション発行の合計」「不正な管理処理の合計」を別項目にする。
- 期待値はケース内の全入力が終わったときの状態・累計。ログは「入力1/3」などと各処理の変化を示す。入力2だけの期待値として表示しない。
- 未接続、ループ上限、待機残存は不合格。最大200ステップと失敗時の状態不変は既存エンジンと同じ。

## UIと配置

エフェクトは「失敗回数 2 → 3 (+1)」「ロック false → true」などを表示し、処理・前提条件・変わる値はフローティング説明にも明記する。処理名とケースの観点で同じ言葉を使う。

既存のブロック移動・矩形選択・処理の追加削除を使う。未配置は各ブロック1個。開始ブロックは削除不可。総合には不要候補として「監査」を含めるが、監査件数は正解条件にしない。
