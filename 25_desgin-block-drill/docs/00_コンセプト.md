# 設計ブロックドリル — コンセプト

## 目的

個々の仕様や処理は理解できても、処理同士の依存関係や全体構造を見落としてしまう。その問題を、小さなシステムを**組み立て、動かし、失敗を観察して修正する**体験で学ぶ。

学習対象は業務の目的やプログラミング文法ではなく、**システムの構造・状態・処理順序・依存関係**。設計図が一見もっともらしくても、動かすと予想外のことが起こる面白さを中心にする。

## 体験の核

- 最初からすべて作らせず、ある程度できた処理フローを渡す。
- 学習者は処理ブロックの接続、成功・失敗の分岐、ブロック内の操作カードの選択・順序を編集する。
- Playすると注文などの「荷物」がキャンバス上を流れる。処理が詰まれば荷物が止まり、後続が滞留する。
- 荷物をクリックすると、現在の状態・データ・直近の処理・停止理由がわかる。
- テストケースを変えると、正常注文では見えなかった欠陥が露出する。
- 修正して別のテストが壊れることもある。局所ではなく全体の構造を考え直す。

## 象徴的な失敗

**キャンセル処理は失敗したのに「キャンセル完了メール」が送信される。**

これはランダムな演出ではない。キャンセル処理の失敗経路が通知へつながっている、または通知がキャンセル成功状態を確認しない、といった設計上の因果関係によって起こす。

## 画面構成

- **左：テストケース** — 通常注文、在庫不足、キャンセル、複数注文、決済失敗など。
- **上：実行操作** — Play、Pause、Step、Reset、速度、現在の実行状況。
- **中央：設計キャンバス** — 処理ブロック、接続線、動く荷物、停止・待機・分岐。
- **詳細・ログ** — 荷物の状態、共有在庫、処理イベント、通知履歴、テストの期待値との差。

## 問題作成の原則

1. トンチクイズにしない。隠れた業務ルールで不意打ちしない。
2. 操作カードの「正解の個数」を示さず、動かして検証させる。
3. 不正解は単なる×ではなく、観測可能な結果や副作用にする。
4. 失敗の原因は、状態・処理ログ・接続をたどれば説明できるようにする。
5. 初期は小さく、正常系と失敗系を数件。徐々に複数注文や再実行へ広げる。
6. テストは段階的に公開しても、後出しの不合理なルールは増やさない。
