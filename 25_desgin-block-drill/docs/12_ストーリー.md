# 設計ブロックドリル — ストーリー・案件展開メモ

作成日：2026-11-01  
状態：アイデア・構成案（未確定、2026-11-01追記）

## 1. 方向性

設計ブロックドリルを、短いストーリーが挟まるステージクリア型の設計シミュレーションとして育てる。

- プレイヤーは架空のSES企業に入社し、なぜか経験豊富なエンジニアとして客先に配属される。
- バグだらけの業務システムを、ブロックの接続・順序・分岐・状態遷移を調整して修正する。
- 同じ案件の「初級 → 中級 → 上級 → 総合」を順に解き、クリアごとに短い会話イベントを挟む。
- **難易度は章ごとにリセットする波形**：新案件の初級は前章の総合より易しくし、新しい業務を理解してから段階的に難しくする。全編を通じた単調な難易度上昇にはしない。
- 案件が変わると、扱う業務・設計上の問題・主人公の立場も変化する。
- 最初はSESあるあるの小話。後半では事件に巻き込まれ、最後は世界を救うくらいまでスケールアップしてもよい。
- 物語は学習の動機づけであり、主役は「組み立てる → 動かす → おかしさに気づく → 修正する」の体験。

仮コピー：**組み立てて、動かして、設計のつながりを考える。**

## 2. 既存の注文システム編

現状の初級・中級・上級・総合の構成を維持する。ストーリーのために問題を細分化しない。

| 区切り | 物語上の依頼 | クリア後の会話イメージ |
|---|---|---|
| 導入 | 初出勤。営業が提出したスキルシートでは「経験5年」。注文システムの修正を頼まれる | 「え、経験5年って書いてある……？」 |
| 初級 | まず普通の注文を通す | 「助かった！ ところでキャンセルの問い合わせも来ててさ」 |
| 中級 | キャンセル系の不具合を直す | 「キャンセル失敗なのに完了メールが飛んでた件、直った？」 |
| 上級 | 複数条件・例外が絡む処理を修正する | 「個別には動くんだけど、変な組み合わせで壊れるらしい」 |
| 総合 | 既存の複数テストを通して整合性を確認する | 「本番いけそう！ ……来週から別案件ね」 |

※問題内容の細部は既存実装を優先。上表は会話の仮案であり、実際のテストケースと整合させてから確定する。

### 会話の長さ

- 開始時：2〜4吹き出し程度。
- 各クリア時：1〜3吹き出し程度。
- 既読イベントはスキップ可能。
- 再挑戦や検証の邪魔をしない。
- 主人公を無能扱いし続けない。周囲の無茶な依頼に振り回されつつ、少しずつ仕事を任される存在にする。

## 3. 難易度設計：章が変わると一度やさしくなる

各案件は「初級 → 中級 → 上級 → 総合」の4段階。総合をクリアしたら次案件の**やさしい初級**へ戻り、新しい題材に慣れる余白を作る。新しい章では、問題の難しさはいったん下げ、新しい業務の見方を一つ導入する。一方、編集操作の解放は章をまたいで累積させる。

```text
難しさ
  高 │       ／＼          ／＼          ／＼
     │      ／  ＼        ／  ＼        ／  ＼
  低 │ ＿＿／      ＼＿＿／      ＼＿＿／      ＼
     └──────────────────────────────→ 進行
         注文編         承認編         認証編
         初→中→上→総   初→中→上→総   初→中→上→総
```

- **初級**：その案件の基本フローと新しい概念を知る。少ないブロック、単純な失敗例。
- **中級**：その業務特有の例外（キャンセル、差戻し、追加認証失敗など）を扱う。
- **上級**：複数条件・状態・再実行が絡む不具合を扱う。
- **総合**：個別に直したものをまとめて検証し、全体の整合性を見る。
- 次章の初級は、前章総合より明確にやさしくする。ただし**既習の考え方は使える**ため、学習者には成長を感じさせる。
- ストーリーも「大案件を完遂 → 新現場で小さなトラブルから再スタート」にする。

## 3.1 操作の段階的解放：第1章はドラッグなし

**問題の難しさは章ごとに上下するが、プレイヤーが使える操作は少しずつ増える。** 初回からブロックの配置・選択・接続・条件編集をすべて要求しない。

| 段階 | 操作範囲 | 未配置ブロック | ねらい |
|---|---|---|---|
| 第1章：注文システム | **ドラッグなし**。あらかじめ配置されたブロックの接続や条件を修正し、実行・検証する | 原則なし | 処理の流れ、分岐、状態の変化を読むことに集中 |
| 第2章：承認ワークフロー（案） | 既存操作に加え、必要なブロックをパレットからドラッグして配置 | 少数。最初は必要なものが分かりやすい | 「足りない処理」を見つけて組み込む |
| 第3章：認証・セキュリティ（案） | 配置・接続に加え、必要なブロックを選び、不要なものを使わない | 種類と数を増やし、ダミーも混ぜる | 取捨選択、条件の組み合わせ、失敗時の遮断 |
| 後半：複合案件・SF防衛（案） | 複数の候補から構造全体を組み立て、例外系を検証 | 多数。ただし無制限に増やさない | 全体設計、依存関係、安全側の停止 |

- **第1章ではブロックを動かせないことをUIでも明示**し、ドラッグできそうな見た目や不要なパレットを出さない。Play／Pause／Stepとログ確認は最初から使える。
- 未配置ブロックは、章が進むほど増える。単なる物量ではなく、**不足している処理の発見 → 候補からの選択 → 不要な処理の除外**という思考の段階を増やす。
- 各章の**初級は少数ブロック・単純なテスト**に戻す。操作の解放済み機能は残すが、すべてを毎回使わせる必要はない。
- ドラッグの解放時には、短いチュートリアルを一度だけ挟む。ストーリー上は「今回は部品も自分で追加して」と依頼される程度でよい。
- 既存エンジンでは `allowDrag`、`availableBlocks`、`distractorBlocks` のような**ステージ設定**で編集権限とパレット内容を切り替える方針（キー名は仮）。
- 操作制限は難易度調整のためであり、プレイヤーを不必要に縛らない。再挑戦・検証は引き続き自由。

## 4. 案件候補とブロックで学ぶこと

| 案件 | 基本フロー | 起こせる事故・面白さ | 主な設計テーマ |
|---|---|---|---|
| **経費精算・承認** | 申請→上長承認→経理確認→振込 | 却下なのに振込、差戻しなのに承認済み、二重振込 | 承認ゲート、権限、状態遷移、重複防止 |
| **ホテル予約** | 空室確認→仮押さえ→決済→確定 | 二重予約、キャンセルしても部屋が戻らない | 共有資源、排他、期限、整合性 |
| **倉庫・出荷** | 入荷→検品→棚入れ→引当→出荷 | 検品NGが出荷、在庫があるのに出せない、滞留 | 前提条件、キュー、待機、分岐 |
| **工場の生産ライン** | 材料投入→加工→検査→組立→出荷 | 不良品流出、再加工の無限ループ、工程渋滞 | ループ、停止条件、処理能力 |
| **勤怠・給与** | 打刻→勤務集計→申請→承認→給与計算 | 休暇が欠勤扱い、二重集計、承認前に確定 | 集計、例外、確定処理、締め |
| **問い合わせ・チケット管理** | 受付→分類→担当割当→対応→完了 | たらい回し、二重担当、未解決なのに完了通知 | 責務分担、状態遷移、再オープン |
| **会員登録・認証** | 仮登録→確認→本登録→権限付与 | 未確認で有効化、退会後も権限が残る | 認可、期限、失効、セキュリティ |
| **検査結果通知** | 受付→検査→確認→承認→通知 | 未承認の結果を通知、検体の取り違え | データ対応付け、承認、重大な副作用 |
| **都市インフラ** | 検知→異常判定→隔離→予備系→復旧 | 障害の連鎖、復旧処理が別の設備を停止 | 障害伝播、依存関係、フェイルセーフ |

### 案件選定の基準

1. ブロックをつなぎ替える意味が明確で、結果をアニメーションやログで観察できる。
2. 正常系だけでなく、失敗・取消・差戻し・再実行などに自然な理由がある。
3. 初級から総合へ難しくできるが、同じ正解パターンの焼き直しにならない。
4. 既存エンジンで表現できる範囲を優先し、新機能は案件ごとに少しずつ追加する。
5. ルールは後出しせず、仕様・状態・実行結果から推理できる。

**次の実装候補は経費精算・承認ワークフロー。** 注文編の「物とお金」に対して「人の判断・権限・差戻し」が加わる。

## 5. 大まかなキャリアと物語の拡張

- **第1期：現場デビュー** — 注文システム。壊れたフローを直す。
- **第2期：案件を渡り歩く** — 経費精算、予約、倉庫など。業務によって異なる設計の勘所を知る。
- **第3期：一人前？** — 工場、認証、複数システム連携。単純なバグ修正から原因調査・設計判断へ。
- **第4期：事件編** — 過去の案件で見た不自然なデータや障害が、別の案件とつながっていることに気づく。
- **最終期：世界を救う仕事** — 都市インフラや大規模連携システムを扱う。何を優先して守るか、という設計判断へ。

伏線は最初から作り込みすぎない。初期案件は単独で楽しめるようにし、後からつなげられる余地を残す。

エンディング案：世界を救った後、営業から「来月の契約単価、据え置きでお願いできますか？」と連絡が来る。

## 6. 実装方針（軽量）

最初は会話イベントの追加だけでよい。

```text
案件（注文システム）
  ├─ 初級：開始イベント → 問題 → クリアイベント
  ├─ 中級：開始イベント → 問題 → クリアイベント
  ├─ 上級：開始イベント → 問題 → クリアイベント
  └─ 総合：開始イベント → 問題 → クリアイベント → 次案件
```

- イベントはデータ駆動（案件ID、難易度、タイミング、話者、本文）。
- 進捗・既読情報はブラウザの `localStorage` に保存。
- クリア済みステージは再挑戦可能。
- イベントを読まずに問題へ進めるスキップ機能を用意。
- 演出を入れても、Play／Pause／Step／ログ確認／全ケース検証という学習の核は変えない。

### イベントデータ例（イメージ）

```json
{
  "caseId": "order-basics",
  "events": {
    "intro": [
      { "speaker": "営業", "text": "経験5年の即戦力として話を通しておきました！" },
      { "speaker": "主人公", "text": "そんな話は聞いてないんですが……" }
    ],
    "afterBeginner": [
      { "speaker": "先輩", "text": "注文が通った！ ところでキャンセルも変なんだよね" }
    ]
  }
}
```

## 7. 架空の会社名と実在企業との距離

「エンジニアのナカマ社」は、実在した「エンジニアのミカタ」のオマージュとして考案された仮名。ただし、2026年秋に旧「エンジニアのミカタ」をめぐるスキルシートの経歴詐称疑惑などが報じられており、名前の類似と「経歴を盛られて配属」という筋が重なると、特定企業への事実の指摘と誤解される可能性がある。

**公開版では、社名をもう少し離すことを推奨。** 例：「株式会社とりあえず技研」「株式会社なんとかソリューションズ」など。**現在の有力候補は「株式会社コウカンゲン」**。何を還元するのか不明、という軽い言葉遊びを軸にする。実在企業の直接的な模倣より、どこかおかしい架空の会社として扱う。

また、現実の報道については「一部のスキルシートに誇張や事実と異なる記載があったとの会社側の説明」と、「組織的な指示などに関する告発側の主張」を区別する。ゲーム中の架空企業の設定を、実在企業に関する確定事実として扱わない。

※フィクション表記は有用だが、実在企業との混同を完全に防ぐものではない。

## 8. 追加案件：セキュリティ編から世界を救う最終章へ

### セキュリティ編（新しい章の初級はやさしく）

| 段階 | 依頼 | ブロック向きの事故 | 学ぶこと |
|---|---|---|---|
| 初級 | パスワード＋追加認証 | パスワードだけでログイン成功 | AND条件、認証状態 |
| 中級 | ログイン失敗の扱い | 失敗回数を超えてもロックされない | カウンター、閾値、状態遷移 |
| 上級 | 権限とセッション | 一般ユーザーが管理機能を使える／ログアウト後も操作可能 | 認証と認可、権限、失効 |
| 総合 | 複数の認証・権限ケースを検証 | 一つの修正で別の経路が開く | セキュリティ条件の網羅、整合性 |

※実際の認証システムを再現する教材ではなく、**状態・条件・許可／拒否の設計**を理解するための抽象化された演習とする。

### 最終章：架空の地球防衛システム

現実の兵器の発射手順・制御を模倣するのではなく、**SFの防衛装置**を使った安全設計の寓話にする。失敗時には漫画的な大爆発、成功時には人類救済。演出は派手でも、原因は状態表示・ログで追えること。

| 段階 | 依頼 | 見せたい失敗 | 学ぶこと |
|---|---|---|---|
| 初級 | 安全確認の基本 | 確認NGなのに装置が動く | 条件判定と安全側への停止 |
| 中級 | 通信途絶・確認失敗 | 情報が欠けたのに動作を続行 | 不明状態の扱い、フェイルセーフ |
| 上級 | 動作中の異常 | 途中で異常になっても止まらない | 状態変化、停止条件 |
| 総合 | すべての状況を検証 | 個別には正しくても組合せで大惨事 | 全体検証、設計判断 |

**演出原則**：失敗は「ドカーン！」と大げさに。成功は地球が無事。繰り返し試す楽しさを作る。ただし単なる当てずっぽうにしない。

### 物語のトーン

- **教材は真面目、会話はどこまでもしょうもなく、短く。** 1〜3吹き出し程度でサクッと挟む。
- 特定の実在企業や人物を生々しく攻撃しない。悪意のある悪徳企業ではなく、悪意はないのに何かが変な「株式会社コウカンゲン」。
- 章を進めると案件・キャリア・事件の規模が拡大するが、会話のしょうもなさは維持。
- 例：世界を救った後の作業報告書の作業場所は「客先常駐」。世界を救っても単価は据え置き。
- 「爆発」はコミカルなフィクションの結果演出であり、実害や現実の被害を細かく描かない。

## 9. 当面の作業

1. 注文システムの既存4段階とテスト内容を照合し、開始／クリア時の台詞を確定する。
2. 第1章をドラッグなしにし、章ごとの操作解放・未配置ブロックの増加をステージ設定として整理する。
3. 既読・スキップ・再挑戦を含む最小イベントUIを実装する。
4. 次案件として経費精算の初級〜総合を設計する。
5. 案件ごとの学習テーマを重複させないよう整理する。
6. 「株式会社コウカンゲン」を仮採用し、実在企業との混同がないか公開前に確認する。
7. セキュリティ編とSF防衛編のステージ案を、既存エンジンで実装可能な範囲から検討する。
