# 設計ブロックドリル — 問題エンジン

## 目的

学習者が組み替えた設計グラフを、同じ入力なら同じ結果になるように実行する。正解ブロックの一致判定ではなく、**実際の状態遷移と副作用**で成否を判定する。

## 責務の分離

1. **問題定義**：初期設計、編集可能な部分、候補操作、テスト、業務ルール。
2. **設計グラフ**：ノード、エッジ、成功／失敗分岐、ブロック内操作列。
3. **実行状態**：注文、共有在庫、通知履歴、各ブロックのキュー。
4. **シミュレーター**：ステップ実行、前提条件評価、状態更新、遷移。
5. **イベントログ**：操作結果と状態差分を時系列で保持。
6. **判定器**：最終状態と禁止副作用を検査。
7. **UI**：イベントを再生し、荷物移動や詰まりを表示。実行ロジックを持たない。

## 設計グラフ

有向グラフとして扱う。ノードは処理ブロック、エッジは移動先。各ブロックには操作カード列を持たせる。成功／失敗の出力先は別に設定できる。

初期版は無制限のループや任意の並列実行を避け、最大ステップ数を設ける。ループ上限に達した場合は停止イベントを記録する。

## 操作カード

操作は名前、前提条件、成功時の状態更新、失敗理由、出力イベントを定義する。学習者は選択・順序変更を行う。必要なカード枚数は教えない。

例：

| 操作 | 成功条件 | 成功時 | 失敗時 |
|---|---|---|---|
| 在庫引当 | 在庫が数量以上 | 在庫減算、引当記録 | 在庫不変、失敗 |
| 引当解除 | 引当記録がある | 在庫加算、引当解除済み | 在庫不変、失敗 |
| 返金 | 決済済み | 返金済みに変更 | 返金せず失敗 |
| キャンセル確定 | 必要な後処理が成立 | キャンセル成功 | キャンセル失敗 |
| 完了メール送信 | **設定された条件による** | 通知履歴に追加 | 送信なし |

最後の通知操作は、学習者が条件チェックを省いた設計にできる。**エンジンはメール送信を禁止して救済しない**。誤送信という結果を起こしてから、テスト判定で検出する。

## ステップ実行

1ステップは基本的に「1荷物の1操作」。

1. 次に実行する荷物・操作を選ぶ（初期版はFIFO）。
2. 操作の前提条件を評価する。
3. `success` / `failure` / `wait` / `no_op` を返す。
4. 成功時の状態差分を原子的に適用する。失敗時は原則として変更しない。
5. ログに操作、結果、状態差分、理由を記録する。
6. 成功・失敗・待機に応じて遷移または停止する。
7. UIにイベントを渡し、荷物や通知を描画する。

途中で失敗した複数操作のロールバックは、初期版では自動的に行わない。後処理が必要なら明示的な操作としてモデル化する。

## 誤通知の実例

初期グラフの欠陥例：

```text
キャンセル要求
  → 在庫引当解除 ─ 成功 → キャンセル確定 ─ 成功 → 完了メール
                   └ 失敗 → キャンセル失敗 ────────→ 完了メール
```

通知ブロックがキャンセル成功状態を確認しない場合、以下が発生する。

```text
#12 ORD-002 在庫引当解除: failure (reservation_not_found)
#13 ORD-002 cancellationStatus: requested -> failed
#14 ORD-002 キャンセル完了メール: sent
#15 判定失敗: キャンセル失敗時に完了通知が送信された
```

修正手段は一つに限定しない。失敗経路の接続変更、通知前の条件判定、成功確定の順序見直しなど、**期待する状態と副作用を満たせば正解**とする。

## テスト判定

実行経路の形そのものを固定正解にしない。テストごとに次のような検証を定義する。

- 注文状態が期待値か
- 共有在庫が期待値か
- 引当数量・返金・出荷指示が整合しているか
- キャンセル失敗時に完了メールがないか
- 通知や返金が重複していないか
- 荷物が待機のまま残っていないか

判定結果は、期待値・実際値・関連イベントを返す。原因そのものは段階的なヒントで示す。

## テストの独立性

個別テストは初期状態をコピーして実行する。一括実行も各テストを独立させる。複数注文の相互作用は、共有状態を持つ**単一の複合シナリオ**として定義する。

## データ定義例（概念）

```json
{
  "id": "cancel-notification",
  "initialGraph": { "nodes": [], "edges": [] },
  "allowedOperations": ["releaseStock", "markCancelFailed", "sendCancelCompleted"],
  "tests": [
    {
      "id": "TC-03",
      "initialState": { "inventory": { "ITEM-A": 8 } },
      "events": [{ "type": "cancel", "orderId": "ORD-002" }],
      "assertions": [
        { "path": "orders.ORD-002.cancellationStatus", "equals": "failed" },
        { "event": "cancelCompletedEmail", "count": 0 }
      ]
    }
  ]
}
```

上記は構造のイメージであり、実装時には注文初期データやイベント投入規約を補う。

## デバッグ・ヒント

- 第1段階：期待値と実際値の差。
- 第2段階：該当荷物の実行履歴。
- 第3段階：失敗した操作と前提条件。
- 第4段階：関係するブロックや接続を示す。

## 実装順序

1. 固定データモデル、純粋な操作関数、状態更新。
2. 1荷物・1操作ずつの決定的な実行。
3. ログとアサーション。
4. キャンバスへのイベント反映。
5. 操作カードの編集。
6. 分岐・接続の編集。
7. 複数荷物・共有在庫シナリオ。

**最大の注意点**：問題作者が失敗を演出するために状態を直接書き換えない。どの失敗も定義された操作と接続の結果として発生させる。
