# 設計ブロックドリル：PV用の動画素材撮影方針

参考：[調査・報告ドリルの撮影方針](../../../26_report-drill/docs/promo/00-promo-capture.md)

Webアプリ「設計ブロックドリル」の、X投稿用プロモーション動画に使う素材を撮影するための方針です。後で編集AIへ素材を渡し、30〜40秒程度のPVにまとめます。

**会話パートとタイトルは静止画で構いません。設計パートは実際にテストを連続実行し、処理が進んで Pass／Fail が付いていく様子を動画で撮影してください。**

PVの編集は撮影作業に含めません。会話の面白さに加え、「ブロックを直すとテスト結果が変わる」遊びが伝わる素材を揃えることが目的です。

## 1. 事前調査と撮影対象

開発元は `25_desgin-block-drill/src/` です。HTTPサーバー経由で `src/index.html` を開き、実際のブラウザ画面を撮影してください。

公開先として設定されているURL：
https://kaku3.github.io/workbooks/design-block-drill/index.html

撮影時はローカル版・公開版のどちらを使用したかと、対象のコミットを成果物のREADMEに記録してください。以下は現行ソースを調査して選定した候補であり、撮影済み素材の一覧ではありません。

| 確認するもの | 参照先 |
|---|---|
| タイトル・ボタン・画面構成 | `src/index.html` |
| 全ケース検証、Pass／Fail、結果演出 | `src/app.mjs` |
| 問題の初期設計、テスト | `src/drills.mjs`、`src/data.mjs`、`src/approval-drills.mjs`、`src/security-drills.mjs` |
| ストーリー進行と会話の表示条件 | `src/story.mjs`、`src/story-ui.mjs` |
| 実際に表示されるセリフ | `src/story-data.mjs` |
| 会話原稿 | `docs/story/01_order.md`、`02_approval.md`、`03_security.md` |
| 設計修正の参考 | `docs/drill/`、`tests/drills.mjs` |

原稿と生成済みデータが食い違う場合、撮影対象の実画面を優先してください。会話データに存在しても通常の進行で再生されないイベントは、撮影候補へそのまま採用しないでください。現行実装では第1章の総合クリア後は次ステージへ進み、`01-04.clear` の会話は再生されません。終了会話は第2章・第3章末を候補にします。

## 2. 素材の構成

同じ問題について「初期設計で検証 → 設計を修正 → 再検証で全成功」を揃えてください。設計パートの主素材には、第1章の総合問題 `order-system` を推奨します。

| ID | 場面 | 形式 | 撮影内容・用途 |
|---|---|---|---|
| 01-title | タイトル | PNG | タイトルとコピーが読める画面。冒頭または締め用 |
| 02-intro | `01-01.intro` | PNGを発言ごと | 営業「経験は5年くらいで！」→あなた「未経験ってお伝えしましたよね…？」。導入の掛け合い |
| 03-before | `order-system` の初期設計 | WebM | 「全ケース検証」を押し、各ケースの Pass／Fail と最後の集計まで連続撮影。失敗を見せる主素材 |
| 04-repair | 同じ問題の修正操作 | WebM | ブロック選択、接続先の変更、操作カードの並べ替えなど。短く使える修正場面 |
| 05-after | 同じ問題の修正後 | WebM | 再び全ケース検証。ケースが順に Pass となり、全成功と Excellent が表示されるまで撮影 |
| 06-banter | `02-03.intro` など | PNGを発言ごと | 「何回押したんですか？」「通るまでです。」「なるほど通るまでですね。」。会話の面白さを見せる差し込み |
| 07-outro | `02-04.clear` または `03-04.clear` | PNGを発言ごと | 「……セキュリティ案件ですよね？」「次は平和な案件がいいですね。」などのオチ |

必須はタイトル、導入会話、初期設計の連続検証、修正操作、修正後の連続検証です。余裕があれば追加の掛け合い・終了会話も揃えてください。前後の会話は静止画で渡せばよく、文字送り全体の録画は不要です。

30〜40秒の完成尺に合わせて、撮影素材を短く打ち切らないでください。連続検証は開始から最終集計までを残し、編集時に使いたい区間を切り出せるようにします。修正操作は5〜15秒程度の短いクリップもあると便利です。

## 3. 設計パートの撮影手順（最優先）

### 初期設計の連続検証

1. 撮影専用のブラウザコンテキストで `src/index.html?drill=order-system&fresh=1` を開きます。案件概要などのダイアログを閉じ、画面を整えます。
2. 設計キャンバス、テストケース一覧、試験詳細、実行ログが見える構図にします。ブロック編集欄は検証時には閉じます。
3. 録画開始後、0.5〜1秒の余白を取り、「全ケース検証」（`#batch`）をクリックします。
4. ケースが順に切り替わり、荷物の移動・処理の強調・ログの追加・Pass／Fail の判定が表示される流れを連続して撮影します。
5. 最終ケースと集計演出まで記録します。現行の初期設計は7件中TC-02だけが Pass、残り6件が Fail となる想定です。撮影時の実測値も記録してください。

### 修正操作

同じ問題を画面操作で修正し、変更が分かる場面を撮影します。`order-system` の修正例は以下です。

- 「在庫を確保」の成功先を「決済する」へ変更する。
- 「キャンセル後処理」を引当解除 → 返金 → キャンセル確定の順にする。
- 「キャンセル失敗」の成功先を終了へ変更し、完了通知へ進めないようにする。

接続線やカードの順番が実際に変わるところを残してください。修正内容の詳細は `docs/drill/01-04_order-system.md` を参照します。第1章はブロック配置固定なので、ブロック移動を見せたい場合は第2章以降を追加撮影します。

### 修正後の連続検証

1. 修正した設計のまま、もう一度「全ケース検証」を押します。
2. 過去の結果が消え、先頭ケースから順に再生され、新たに Pass が付いていく流れを撮影します。
3. 最後のケースから `7 / 7 ケース成功`・`Excellent` の結果演出まで残します。
4. 最終結果の代表静止画も保存します。

**判定済みの一覧や結果画面だけを動画にして完了としないでください。未判定 → 実行中 → Pass／Fail → 次のケース、という画面変化が必須です。**

初期設計では Pass と Fail が混在し、修正後はすべて Pass になる対比を使います。同じケースが修正前は Fail、修正後は Pass になったと分かるよう、ケースIDと判定が読める区間を残してください。処理操作の「失敗」とテストの Fail は別なので、テスト結果は試験詳細とケース一覧で確認します。

## 4. 撮影速度と画角

- ビューポートと録画サイズは原則1920×1080、16:9に揃えます。録画が縮小されていないことを確認します。
- 実行速度はゲーム標準の1xを基本にし、長い場合のみ標準の2xを使います。使用速度は `scenes.json` に記録します。
- ケース終了時の Pass／Fail のスタンプ、一覧の更新、次ケースへの切り替わりを残します。短い判定表示を飛ばさないでください。
- 元の連続録画を保存した上で、編集候補として「Fail が続く区間」「Pass が続く区間」「最後の成功判定と Excellent」をそれぞれ5〜15秒程度で指定すると使いやすくなります。
- マウス移動とクリックは自然に見せ、操作箇所を見失わない速度にします。
- 試験詳細が重要なブロックやログを隠す場合は、既存のサイズ変更機能で調整します。必要なら同じ条件の追加テイクを撮ります。
- 録画開始・終了に0.5〜1秒程度の余白を取ります。ただし集計画面は自動で閉じるため、表示を検知してすぐ静止画も保存します。
- ゲームのUI・セリフ・アニメーション・検証ロジックは維持します。DOMの書き換えで結果を作ったり、実行を省略して判定だけ表示したりしないでください。

## 5. 会話・タイトルの静止画

タイトルはフォントと画像の読み込みが終わり、画面が安定した状態で撮影します。

会話はタイプライター表示の完了を待ち、立ち絵・話者名・セリフ全文が見える状態で保存します。掛け合いは一発言につき一枚とし、連番で順序が分かるようにしてください。文字の途中や、画像が読み込み中の状態は使いません。

使えそうなセリフは [01-promo-lines.txt](01-promo-lines.txt) に抽出しています。イベントID・発言番号・話者を使って撮影対象を特定してください。強調記号を外し、画面上の改行をテキストの改行に置き換えています。

会話はストーリーモードで撮影します。`?drill=ID` の自由演習では会話は開きません。後半のイベントには進捗の解放が必要です。通常プレイまたは撮影専用コンテキスト内の進捗準備で到達し、準備方法をREADMEへ記録してください。章末会話は、その章の総合問題をストーリーモードで全ケース成功させ、結果演出後に撮影します。

## 6. Playwrightと再実行性

撮影を実施する際はPlaywrightでブラウザを操作し、設計パートは画面録画とトレースの両方を有効にしてください。タイトル・会話はPNGとトレースを保存します。

- シーンごとにトレースを分けます。録画はコンテキストを閉じて保存を完了させます。
- ローカルの開発元を撮影する場合、アプリ本体のビルドは不要です。HTTPサーバーの起動方法、Playwrightの依存関係と実行コマンドをREADMEへ記録します。
- 撮影専用コンテキストを使い、普段のプレイの保存設計・進捗を変更しないでください。
- `fresh=1` は自由演習で初期設計を用意するために使います。修正後の録画前に再指定すると修正が消えるため、初期化と再検証を分けます。
- 状態の待機には、要素の表示、実行中ケース、結果、ダイアログの状態を使います。長い固定sleepだけで制御しないでください。
- 連続検証は問題により長さが変わるため、ケース数に見合うタイムアウトを設定します。最後まで完了したことを確認します。
- 既存の補助機能や必要最小限の撮影用準備は使用できます。通常プレイにデバッグUIや撮影用データを残さず、本番ロジックとセリフは変更しません。

## 7. 成果物

撮影時の出力は、このディレクトリ内の `promo-capture/` にまとめます。

```text
promo-capture/
  README.md
  scenes.json
  capture.mjs（または capture.spec.ts）
  clips/
    03-before.webm
    04-repair.webm
    05-after.webm
  traces/
    01-title.zip
    02-intro.zip
    03-before.zip
    04-repair.zip
    05-after.zip
    ...
  screenshots/
    01-title.png
    02-intro-01.png
    02-intro-02.png
    03-before-result.png
    05-after-result.png
    06-banter-01.png
    ...
  01-promo-lines.txt
```

最後に `promo-capture.zip` にまとめます。セリフ抽出ファイルも同梱してください。

`scenes.json` には以下を記録します。

- `scene_id`、説明、PVでの用途、素材種別（`image` / `video`）
- 章・ステージ・`drill_id`、会話のイベントID・発言番号、登場人物、主なセリフ
- 動画・静止画・トレースの相対パス
- 設計の状態（初期 / 修正中 / 修正後）、修正内容、実行速度
- 各ケースのIDと実測した Pass／Fail、最終成功件数
- 動画内のおすすめ区間と、ケース判定・集計の時刻（取得できた場合）

静止画の動画時刻は `null` とし、未取得の時刻は推測で埋めず「未計測」と記載してください。

## 8. 撮影完了時の確認

- 動画ファイルを実際に再生し、ゲーム画面が映っていることを確認する。
- 初期設計の連続検証で Pass と Fail の両方が見える。
- 修正後の連続検証で順に Pass が付き、全成功の集計と Excellent が見える。
- 各ケースの確定判定と、ケース間の切り替わりが途中で切れていない。
- 修正前後で同じ問題・同じテストを使用している。
- タイトル・会話は全文と立ち絵が見え、発言順と話者が追える。
- トレースがPlaywrightで開け、`scenes.json` と実ファイルが対応している。
- ZIPに再実行手順、素材、シーン一覧、セリフテキストが揃っている。

撮影作業の実施時はスクリプト作成だけで終えず、実行・再生確認まで行ってください。結果の報告では、撮影したシーン、保存先、未撮影の候補、未解決の問題を区別して記載してください。
