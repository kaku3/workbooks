# コミュ力診断アプリ 仕様書（実装準拠）

メンターが対象者を観察し、コミュニケーション上の傾向を可視化して介入方針を検討するための静的Webアプリ。

---

## 1. 概要

| 項目 | 内容 |
|---|---|
| ターゲット | エンジニア・IT職種のメンター・育成担当者 |
| 入力者 | 主にメンター（観察ベースで回答） |
| 出力 | 良好スコア（Z）・問題タイプスコア（10軸）・上位タイプの対策 |
| 実行形態 | 静的HTML/CSS/JS |

---

## 2. 実装ファイル構成

```
src/
  index.html      ランディング
  check.html      診断入力 + 結果表示
  types.html      タイプ一覧 + 詳細モーダル
  history.html    診断履歴一覧
  data.js         タイプ定義・設問・採点ロジック
  style.css       共通スタイル
  ogp.png         OGP画像
```

---

## 3. ページ仕様

### 3-1. index.html

- ヒーローセクション（診断導線）
- 特長カード
- 11タイプのプレビューカード（モーダルで詳細表示）
- 診断開始CTA

### 3-2. check.html

- 18問の観察式チェック（0〜4）
- 進捗表示付きの固定フッター
- 回答4問以上で結果表示可能
- 結果表示内容:
  - 総合判定
  - Zスコアバー
  - 問題タイプ10軸レーダーチャート（SVG自前描画）
  - 上位3タイプの詳細カード（折りたたみ）
  - 結果URLコピー

### 3-3. types.html

- グループ別ブロック表示（良好 + 4グループ）
- フィルタボタン（すべて / 動機 / 聴き方 / 整理 / 組み立て）
- カードタップで詳細モーダル

### 3-4. history.html

- ローカル保存された直近10件を表示
- 各履歴の名前編集（インライン編集）
- 履歴削除
- 保存済み回答を check.html へ再適用して再表示

## 4. タイプ定義（11タイプ）

### 4-1. タイプID

- 良好: Z
- 動機グループ: M1, M2
- 組み立てグループ: D1, D2
- 整理グループ: S1, S2, S3
- 聴き方グループ: R1, R2, R3

タイプ名対応:

| ID | 名称 | サブ名 |
|---|---|---|
| Z | 「良好」型 | コミュニケーション良好 |
| M1 | 「困っていない」型 | 動機欠如 |
| M2 | 「防衛本能がつよい」型 | ハリネズミタイプ |
| D1 | 「見えてるけど気づかない」型 | 回路未接続 |
| D2 | 「自分視点のまま」型 | 読み手不在 |
| S1 | 「整理できない」型 | 構造化困難 |
| S2 | 「頭の中にあるけど出ない」型 | 言語化困難 |
| S3 | 「具体から動けない」型 | 抽象化困難 |
| R1 | 「聞けていない」型 | 受信困難 |
| R2 | 「止まれない」型 | 出力過多 |
| R3 | 「残らない」型 | 保持困難 |

### 4-2. 各タイプが保持するデータ

- id
- clsKey
- group（Z以外）
- good
- name
- sub
- emoji
- color
- desc
- symptoms
- effective（タイトル + 詳細）
- ineffective（タイトル + 詳細）

## 5. 設問仕様

### 5-1. 設問数と尺度

- 設問数: 18
- 評価尺度: 0〜4
  - 0: 全くない
  - 1: ほぼない
  - 2: たまに
  - 3: よくある
  - 4: 常に

### 5-2. 設問一覧（実装文言）

1. 説明時に、相手向けの要点より自分の思考順で話してしまうことが多い
2. 分からないことがあれば、自分から質問しに来る
3. 作業後の報告で「何を学び次にどう活かすか」を整理できず、同じ構造ミスを繰り返す
4. 概要と詳細を使い分けて説明できる
5. フィードバック後、一時的には改善するが、しばらく経つと元の習慣に戻っている
6. ルールや評価基準を、最小の労力でクリアしようとする
7. 質問したり一緒に考えたりすると答えが出てくるが、一人に任せると出てこない
8. 固有名詞・略語・社内用語を説明なく使う
9. 文章全体の主語・結論・トーンに一貫性がなく、段落ごとに言っていることがぶれる
10. コピペの継ぎ接ぎで、用語定義・前後関係・結論のつながりが崩れた報告になりやすい
11. 作業の意図（何のためにやるか）が言語化されず、報告が事実列挙に終わって次の打ち手につながらない
12. 同じ指摘を複数回しても改善されず、自分からは確認しに来ない
13. 相手の話が終わる前に話し始める、または会話の大半を自分が占有する
14. 指摘を受けると内容確認より先に自己弁護・正当化が出やすい
15. メモを取らない、または取ってもあとで参照できない内容になっている
16. 指示の直後は正確に動けるが、翌日以降は内容を自分で思い出せない
17. 作業中に指示の意図を忘れて、別の方向に進んでいることがある
18. 同じミスを状況を変えて繰り返す（一般化・パターン認識が難しい）

## 6. 採点と判定

### 6-1. スコア計算

各設問にはタイプごとの重み配列を持ち、以下で合算する。

```
scores[typeIndex] += rating[q] * questionScores[q][typeIndex]
```

- 未回答（null）は計算対象外
- scores[0] が Z
- scores[1..10] が問題タイプ（M1〜R3）

### 6-2. 判定ロジック

- z = scores[0]
- top = max(scores[1..10])

| 条件 | 判定 |
|---|---|
| z > 30 かつ top < 20 | 良好 |
| z > 15 かつ top < 40 | 概ね問題なし |
| top < 70 | 要観察 |
| それ以外 | 介入推奨 |

### 6-3. 結果表示可能条件

- 回答済みが4問以上

### 6-4. 正規化

問題タイプ表示用に以下を適用する。

```
normalized = round(max(score, 0) / max(maxProblemScore, 1) * 100)
```

- 負値は0として扱う
- 全値が0以下でも0除算しないよう max(..., 1) を使用

## 7. 結果表示仕様

### 7-1. Zスコア

- Zをバー表示
- 表示用正規化上限は 60

### 7-2. レーダーチャート

- SVGで自前描画
- 軸数: 10
- 表示順:
  - M1, M2, R1, R2, R3, S1, S2, S3, D1, D2
- アニメーション: 約900ms

### 7-3. 上位タイプ

- 問題タイプをスコア降順で並べ替え
- 上位3件を表示
- スコア表示は max(score, 0)

## 8. URL共有・復元

### 8-1. クエリ形式

- パラメータ名: r
- 形式: カンマ区切りの回答列
- 例: ?r=0,1,2,3,4,...

未回答は空文字で保持されるため、連続カンマを含む場合がある。

### 8-2. 復元動作

- 起動時に r を読み取り
- 0〜4 の整数のみ反映
- 4問以上復元できた場合は自動で結果表示（履歴保存はスキップ）

---

## 9. 永続化仕様

### 9-1. 履歴保存

- 保存先: localStorage
- キー: commu-checker-history
- 保持上限: 10件（新しい順）

保存データの1件構造:

```
{
  id: number,
  date: ISO8601 string,
  name: string,
  r: string,
  topTypes: string[]
}
```

### 9-2. 履歴画面機能

- 一覧表示
- 名前編集（クリックで入力欄へ）
- 削除
- check.html への遷移で結果再現

## 11. 既知の実装上の前提

- バックエンド連携なし
- 履歴はブラウザローカルにのみ保持
- 共有人の環境では履歴と復元結果は共有されない
- 診断結果は参考値であり、医療的・心理的診断を目的としない
