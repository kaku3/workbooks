# コミュ力診断アプリ 仕様書

> メンターが対象者を観察し、コミュニケーション上の問題パターンを特定・介入方針を立てるための診断ツール。

---

## 1. 概要

| 項目 | 内容 |
|---|---|
| ターゲット | エンジニア・IT職種のメンター・育成担当者 |
| 入力者 | メンター（対象者を観察した上で回答） |
| 出力 | 問題タイプの該当度スコア＋傾向と対策 |
| 形式 | 静的HTML（1〜3ファイル、外部依存なし） |

---

## 2. ページ構成

```
src/
  index.html     ランディングページ（キャッチコピー＋診断への導線）
  check.html     診断画面（設問＋結果のレーダーチャート）
  types.html     タイプ一覧・詳細（傾向と対策）
```

---

## 3. タイプ定義（11タイプ）

| ID | タイプ名 | サブ名 | 良好フラグ |
|---|---|---|---|
| Z | 「良好」型 | コミュニケーション良好 | ◎ |
| A | 「困っていない」型 | 動機欠如 | ✕ |
| B | 「見えてるけど気づかない」型 | 回路未接続 | ✕ |
| C | 「自分視点のまま」型 | 読み手不在 | ✕ |
| D | 「整理できない」型 | 構造化困難 | ✕ |
| E | 「スイッチ待ち」型 | 文脈依存 | ✕ |
| F | 「頭の中にあるけど出ない」型 | 言語化困難 | ✕ |
| G | 「具体から動けない」型 | 抽象化困難 | ✕ |
| H | 「聞けていない」型 | 受信困難 | ✕ |
| I | 「止まれない」型 | 出力過多 | ✕ |
| J | 「残らない」型 | 保持困難 | ✕ |

各タイプは以下の情報を持つ：
- **説明文**（desc）：タイプの本質的な特徴
- **観察される行動**（symptoms）：メンターが目撃できる具体的な行動
- **有効なアプローチ**（effective）：介入効果が高い方法
- **効きにくいアプローチ**（ineffective）：やりがちだが効果の薄い方法

## 4. 診断設問（17問）→ 改訂版（18問）

採点者：**メンター本人**が対象者を観察して回答する。

スケール：`0＝全くない` / `1＝ほぼない` / `2＝たまに` / `3＝よくある` / `4＝常に`

UI：星または数字ボタン（タップしやすい大きさ）

### 設問リスト（改訂案）

元の設問で曖昧だった箇所（下記 ★ 印）を修正。

| # | 改訂後テキスト | 変更理由 |
|---|---|---|
| Q1 | フィードバックを受けた内容を、次の機会に自発的に反映している | 変更なし |
| Q2 | 分からないことがあれば、自分から質問しに来る | 変更なし |
| Q3 | 改善策を自分で考えて提案したことがある | 変更なし |
| Q4 | 概要と詳細を使い分けて説明できる | 変更なし |
| Q5 | その場では「確かに」と同意するが、翌日には元の行動に戻っている | 変更なし |
| Q6 | ルールや評価基準を、最小の労力でクリアしようとする | 変更なし |
| Q7 ★ | 質問したり一緒に考えたりすると回答が出てくるが、一人に任せると抜ける | 「詰めると」は高圧的なニュアンスがあるため修正 |
| Q8 | 固有名詞・略語・社内用語を説明なく使う | 変更なし |
| Q9 | 文書や報告の粒度がバラバラで、概要と細部が混在している | 変更なし |
| Q10 | 口頭でも文章でも、話が長くなりがちで要点が伝わりにくい | 変更なし |
| Q11 ★ | 作業内容を時系列で列挙はできるが、「つまり何をやったか」がまとめられない | 「時系列の作業記録は書けるが」が不明瞭だったため具体化 |
| Q12 | 同じ指摘を複数回しても改善されず、自分からは確認しに来ない | 変更なし |
| Q13 ★ | 相手の話が終わる前に話し始める、または会話の大半を自分が占有する | 2つの行動を「・」で並記していたため「または」で整理 |
| Q14 | 重要な案件は丁寧にこなすが、日常の作業はどれも一律に雑になる | 変更なし |
| Q15 | メモを取らない、または取ってもあとで参照できない内容になっている | 変更なし |
| Q16 ★ | 指示の直後はできているが、日をまたぐと内容が抜けている（Q5と区別：Q5は「姿勢が戻る」、Q16は「内容が消える」） | 内容区別を注記で明記 |
| Q17 | 作業中に指示の意図を忘れて、別の方向に進んでいることがある | 変更なし |
| Q18 ★（追加） | 物事を一般化・抽象化して「同じパターンだ」と気づくことが少ない | G型（抽象化困難）を問う設問として追加（元の設問が不足気味） |

## 5. 採点・判定ロジック

### スコア計算

```
typeScore[t] = Σ (rating[q] × weight[q][t])  // 全設問ループ
```

- `rating[q]` は 0〜4 の整数（未回答はスキップ）
- `typeScore[Z]` が「良好スコア」
- `typeScore[A〜J]` が各「問題スコア」

### 総合判定

| 条件 | 判定ラベル | 説明 |
|---|---|---|
| Z > 30 かつ max(A〜J) < 20 | 良好 | 目立った問題なし |
| Z > 15 かつ max(A〜J) < 40 | 概ね問題なし | ピンポイントな課題あり |
| max(A〜J) < 70 | 要観察 | 複数パターン重複の疑い |
| それ以外 | 介入推奨 | 優先順位を付けた介入が必要 |

### 最低回答数

4問以上回答しないと結果を表示しない。

## 6. 結果表示

### レーダーチャート

- 軸：10タイプ（A〜J）
- 値：各問題スコアを `max(score, 0)` で正規化（0〜100 に変換）
- Z スコアは別途バーで表示（チャートの軸とは別扱い）
- ライブラリ：外部依存ゼロのため **SVG で自前描画**（または Chart.js を CDN から読み込む選択肢も許容）

### 結果ブロック構成

```
[総合判定バッジ]
[サマリーテキスト（1行）]
[補足テキスト（2〜3行）]

[Z 良好スコア バー]

[レーダーチャート（A〜J の10軸）]

[上位3タイプのカード（タップで詳細モーダルへ）]
  - タイプ名
  - スコア
  - 観察される行動（先頭2件）
  - 有効なアプローチ（先頭2件）

[共有ボタン（URLパラメータに結果を乗せる）]
```

### URLパラメータによる結果共有

診断結果を `?r=0,3,2,4,...` のように回答値をエンコードしてURLに付与し、URLを共有すると同じ結果が再現できる。

## 7. 画面詳細

### 7-1. index.html（ランディングページ）

- **キャッチコピー案**：「その指導、届いていますか？」または「同じことを何度言っても変わらない、その理由がわかる」
- Hero セクション：タイトル＋キャッチコピー＋「診断スタート」ボタン
- 特徴セクション：3〜4つのメリット（アイコン＋短文）
- タイプ紹介セクション：11タイプをカードで並べる（一覧ページへの導線）
- CTA セクション：再度「診断スタート」ボタン

### 7-2. check.html（診断画面）

**ステップ構成**（スクロールまたはスワイプ）

```
Step 0: 説明画面（対象者名入力オプション、回答方法説明）
Step 1〜17: 設問（1問ずつ表示 or 全問スクロール）※UI選択は下記参照
Step R: 結果画面
```

**UI方針（スマホ対応）**

- 全問スクロール表示（スマホで1問ずつめくるより視認性が良い）
- スケールは `0〜4` のタップボタン（最低44px高さ）
- 未回答設問は薄いハイライトで視認性確保
- フッターに「結果を見る」ボタン（スティッキー）

### 7-3. types.html（タイプ一覧・詳細）

- グリッド表示（モバイル：1列、タブレット以上：2列）
- 各カードタップで詳細モーダルが開く
- 詳細モーダル内：説明・観察される行動・有効アプローチ・効きにくいアプローチ
