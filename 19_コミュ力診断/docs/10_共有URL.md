# 共有・持ち運び仕様（実装済み）

最終更新: 2026-05-20

## 1. 背景

90日トレーニングの共有URLは、チェックが増えるほど `check` パラメータが長くなる。
特に「全項目を90日分チェック済み」のケースでURL長が実用上の限界を超えるため、
共有の主軸を URL から JSON export/import に切り替えた。

---

## 2. 現在の仕様（実装準拠）

### 2-1. 診断結果ページ (`check.html`)

- クエリ: `?r=`
- 形式: 回答(0-4)をカンマ区切りで保持
- 例: `?r=0,1,2,3,4,...`
- 圧縮: なし

この方式は質問数が固定で少ないため、URL長は問題化しにくい。

### 2-2. トレーニング共有ページ (`trainings/index.html`)

- 画面上の共有導線は3つ
  - 表示URLをコピー（軽量URL）
  - JSON書き出し
  - JSON読込
- 新規URL生成は軽量パラメータのみ
  - `?type=<type>&subjects=<csv>`
  - `check` は新規生成しない
- URLデコード互換は維持
  - `check` が付いた既存URLは読み込み可能
  - デコード順:
    1. JSON形式（互換レガシー）
    2. `v3` コンパクト形式（現行主力）
    3. 旧レガシー（`key:date|...`）

現行 `v3` の中身:

- 形式: `v3|b:<baseDate>|d:<typeBlocks>`
- 日付は `baseDate` からのオフセット日数を36進数で保持
- キーは `week-<n>-<i>` を `w<base36(n)>i<base36(i)>` に短縮
- 1項目に複数日ある場合、`off.off.off` のように列挙

要するに、旧共有URLの互換読込は残しつつ、
新規共有で巨大URLを生成しない構成に変更済み。

---

## 3. 現行方式の長さ試算

実データ（`src/trainings/data/*.js`）のチェック項目数:

- 合計項目数: 289
- タイプ別: d1=29, d2=29, m1=29, m2=28, r1=29, r2=29, r3=29, s1=29, s2=29, s3=29

試算条件:

- denseケース: 289項目すべてに対し90日すべてチェック
- sparseケース: 289項目すべてに対し1日だけチェック

試算結果（現行 `v3`）:

- denseケース
  - コンパクト生文字列: 69,118 文字
  - Base64URL後 (`check` のみ): 92,158 文字
  - フルURL: 92,246 文字
- sparseケース
  - コンパクト生文字列: 2,070 文字
  - Base64URL後 (`check` のみ): 2,760 文字
  - フルURL: 2,848 文字

結論:

- ご懸念どおり、全日チェックではURLが非常に長くなる。
- 多くの環境で扱いづらい長さになるため、追加圧縮が必要。

## 4. JSON Export/Import 仕様（実装済み）

### 4-1. URL長に関する運用前提

- URL長は RFC 上で一律上限が定義されていない。
- ただし実運用では、ブラウザ・サーバー・プロキシ・社内NW機器で上限が異なる。
- 実務上は 2KB〜8KB 付近で問題化しやすく、4096 文字制限を持つ系も存在する。

したがって、90日全量データの共有を URL クエリへ載せる方式は採用しない。

### 4-2. 共有方式

- 主方式: JSON export/import
- 補助方式: URL共有（軽量パラメータのみ）

URL共有で保持するのは以下に限定する:

- `type`
- `subjects`
- 必要最小の表示モード情報

`check` のような大量データは URL に載せない。

### 4-3. Export JSON 仕様

ファイル名実装:

- `commu-checker-training-export-YYYYMMDD-HHmmss.json`

JSON構造:

```json
{
  "version": 1,
  "app": "commu-checker-training",
  "exportedAt": "2026-05-20T10:30:00.000Z",
  "subjects": ["r1", "d1"],
  "state": {
    "r1": {
      "week-1-0": ["2026-05-01", "2026-05-03"],
      "week-1-1": ["2026-05-02"]
    },
    "d1": {}
  }
}
```

要件:

- `state` は現行 localStorage の構造と互換
- 日付は `YYYY-MM-DD` のみ許可
- 重複日付は export 時に除去
- `app` は `commu-checker-training`
- `version` は `1`

### 4-4. Import JSON 仕様

入力手段:

- ファイル選択（`.json`）
- 将来拡張でテキスト貼り付けを許可してもよい

バリデーション:

- `app === "commu-checker-training"`
- `version` が対応範囲内
- type は許可済み 10 種のみ
- key は `week-<n>-<i>` 形式
- date は `YYYY-MM-DD` 形式

反映方式:

- 「置換インポート」のみ
- インポート実行前に確認ダイアログを表示
- 実行時は既存データのバックアップJSONを自動出力

### 4-5. バリデーション実装

- `app === "commu-checker-training"`
- `version` は 1 以上かつ対応上限以下
- type は許可済み 10 種のみ
- key は `week-<n>-<i>` 形式
- date は `YYYY-MM-DD` 形式
- 有効データ件数 0 のJSONは読込拒否

---

## 5. 互換性方針

URL decode は既存を当面維持:

1. `v3`（現行）
2. JSON `v2`（旧）
3. `key:date|...`（最旧）

ただし新規生成では大量データ付きURLを発行しない。
新規共有は JSON export/import を使う。

---

## 6. 長さに関する判断

dense ケースは現行試算で約 92KB のため、URL共有として不適。
4KB 前後での障害リスクが現実的に高く、仕様として URL 搭載は見送る。

代替として JSON ファイル共有を正規ルートにする。

---

## 7. 画面操作手順

### 7-1. メンターへ共有（推奨）

1. 学習者側で「JSON書き出し」を押す
2. 生成された `.json` をメンターへ送る
3. メンター側で「JSON読込」を押して同ファイルを選択

### 7-2. 表示URLの共有（軽量）

1. 「表示URLをコピー」を押す
2. コピーURLには `type` と `subjects` のみ含まれる
3. チェック履歴本体は含まれない

---

## 8. 実装時の注意点

- 不正 JSON は安全に拒否し、既存データを壊さない
- Import 前に確認ダイアログを出す
- 個人情報は含めない（学習記録のみ）
- バックアップJSONはダウンロードフォルダへ保存される

---

## 9. 受け入れ条件

- Export した JSON を Import して同一状態を再現できる
- 既存 `v3/v2/legacy` URLが読み取り可能
- 新規共有操作で巨大 URL を発行しない
- エラー時に画面が壊れず、既存データも保持される
