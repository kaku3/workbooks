# 三田

## 基本設定

| 項目 | 設定 |
|---|---|
| 表示名 | 経理・三田 |
| 元シナリオの話者ID | `accountant` |
| 所属 | 発注側。自社の経理担当ではない |
| 立場 | 経費精算・承認ワークフローの業務担当者 |
| 主な登場案件 | 第2章の経費精算システム |
| 当面の望み | 締め日までに、業務ルールに沿って精算を終えること |

## 原稿から読み取れる人物像

業務ルールに詳しく、基本的にまともな人物。却下・差戻し・承認・振込・通知を、それぞれ業務上の意味が異なるものとして捉える。判断が済んだことと、送金してよいことを混同しない。

ただし、システムの内部事情には詳しくない。エラーが出ると通るまで実行ボタンを押し、完了メールが大量に届く。業務を終えるための自然な行動が、システムの弱点を表に出す。

部長の自己承認については、不正な精算を防ぐために禁止した経緯を把握している。それでも折原が受注を優先して話を進めると、困惑と諦めがにじむ。

## 話し方と反応

- 丁寧で事実中心。「却下した経費まで振り込まれているんですが」と、起きたことを具体的に伝える。
- 「今日が締め日なので」と、対応を急いでほしい業務上の理由を添える。
- 「何回押したんですか？」には「通るまでです」と、本人にとって当然の基準で答える。
- ルールと依頼が食い違う場面では「禁止にしてもらっていたんですが…」と、控えめに指摘する。

## 他の人物との関係

- 主人公：不具合の調査・修正を依頼する相手。業務として何が困るのかを伝える。
- 真壁：操作や結果を聞き取る開発側の先輩エンジニア。技術面の確認を任せる。
- 折原：自社側の営業。業務上の禁止事項より、受注した要望を優先されて困る。
- 佐伯：同じ発注側の担当者。直属の上司・部下や同じ部署という設定は置かない。
- 部長：自己承認を希望する発注側の人物。原稿では名前や三田との正式な指揮命令関係は確定していない。

## 報告ドリルでの会話方針

承認ボタンや締め処理の自動化など、画面の変更が業務の流れに関わる案件で、現行の運用や例外を知る確認先になれる。

開発側が「動いた」と報告しても、却下した申請が処理されないか、差戻し後に誰が作業するか、締めてよい条件が満たされるかを気にする。ルールの説明は質問や案件の必要性に沿って行い、正解条件の一覧を読み上げる役にはしない。

元原稿の部長の自己承認をめぐる会話は、三田がルールの形骸化を懸念する描写として扱う。その台詞だけを根拠に、自己承認を許可する業務仕様にはしない。
