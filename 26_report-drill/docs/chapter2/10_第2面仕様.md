# 第2面「ボタンひとつのはずでした」仕様 v1

## 位置づけ
案件ID `approval-button`（既存草案の候補を採用）。公開名は暫定「承認画面へのボタン追加」。
第1面で学んだ「仕様書→ログ→ソース→検証」という正攻法は役立つが、それだけでは顧客への回答にならないことを体験させる。

**学習上の狙い**: 調査の取捨選択、要望と目的の分離、変更範囲の見立て、未確定事項を明示した報告。
**ゲーム上の狙い**: 関係ない調査にも手応えがある。佐伯の反応で足りない説明を察する。時間切れでも説教や周回を含めて楽しめる。
攻略用の「目的達成率」「正解の調査ルート」などは画面に出さない。

## 案件の確定事実（今回の設計案）
- 現状: 経費申請には「承認」「却下」があり、却下すると元の申請を編集して再提出する経路がない。
- 顧客の表面的依頼: 「承認画面に差戻しボタンを一つ追加してほしい」。
- 実際の目的: 軽微な入力不備で最初から入力し直す負担と、別途メールで修正依頼する負担を減らす。
- 必要な業務の流れ: 経理/承認者が理由を付けて差戻し→申請者が修正→再申請→改めて承認判断。
- 影響: 画面ボタンだけでなく状態、編集権限、再申請経路、通知・履歴を検討する必要がある。
- 未確定事項: どの項目まで修正可能か、承認経路の再開条件、通知先、工数・納期。現時点で勝手に確定しない。
- 本面の報告は**実装完了報告ではなく、要件整理と次の確認事項の提案**。正確な工数見積りや実装方式の確定は要求しない。

## 最初のカンバン候補
- `依頼と現状を確認する` 20m → 表面的依頼と現行の却下仕様
- `画面仕様書を読む` 20m → ボタン追加のUI候補
- `業務担当に聞く` 30m → 目的（再入力と別連絡を減らす）
- `現行フローを確認する` 30m → 却下で申請が終了する
- `ソースを解析する` 60m → フロント/API/状態処理を解放
- `AIに聞く` 5m → もっともらしいボタン追加案を提示、未検証
- `真壁に聞く` 10m〜 → 状況・準備に応じた反応
- `昼休憩` 60m、`真壁に途中報告` 30m（第1面と同じ基本挙動）

## 調査系統（ID・時間は暫定）
| ID | 調査 | 時間 | 解放 | 得られること |
|---|---|---:|---|---|
| `ab.request` | 依頼と現状を確認 | 20m | 初期 | 依頼内容（要望≠目的） |
| `ab.screen` | 画面仕様書を読む | 20m | 初期 | ボタンを配置できる（技術情報） |
| `ab.business` | 経理の三田に確認 | 30m | 初期 | 入力し直しと別メールが負担 |
| `ab.workflow` | 現行の業務フローを読む | 30m | 初期 | 却下後に編集・再提出できない |
| `ab.source` | ソースを解析する | 60m | 初期 | 技術系調査先を解放 |
| `ab.ui` | ボタン配置を検討 | 45m | 画面仕様 | 配置案（有用だが報告必須でない） |
| `ab.api` | APIの改修点を調べる | 60m | ソース | API追加候補（未確定） |
| `ab.state` | 状態遷移を調べる | 40m | 現行フロー or ソース | 差戻し状態と再申請の流れが必要 |
| `ab.permission` | 編集権限を調べる | 35m | 状態遷移 | 申請者の編集可否・確定すべき制約 |
| `ab.notification` | 通知と履歴を調べる | 40m | 状態遷移 | 差戻し理由、通知、操作履歴への影響 |
| `ab.reapply` | 再申請の経路を確認 | 35m | 業務担当 or 状態遷移 | 修正後の再申請と再承認 |
| `ab.design` | 実装方式を比較 | 90m | API or UI | 複数の実装案。要件確定前は決められない |
| `ab.ai` | AIに聞く | 5m | 初期 | ボタン/APIの一般案。案件固有の根拠ではない |

所要時間・知識増分は既存エンジンに合わせて調整する。**技術調査にも知識やカードを与える**こと。無意味な罠カードにしない。

## 証拠品案（短い見出し・要点）
| ID | 見出し | 要点 | 説明要素 |
|---|---|---|---|
| `ab.requested` | 差戻しボタンの依頼 | 承認画面にボタンを追加したい | 依頼のみ |
| `ab.pain` | 再入力と別連絡が負担 | 軽微な不備でも最初からやり直し | 目的 |
| `ab.current` | 却下後は再編集できない | 現状の却下は申請を終了させる | 現状 |
| `ab.flow` | 修正して再申請したい | 差戻し→修正→再申請→承認 | 業務フロー |
| `ab.state` | 状態の追加が必要 | 差戻し中・再申請などの扱いを決める | 変更範囲 |
| `ab.access` | 編集できる人の確認 | 差戻し中の申請者権限が必要 | 変更範囲 |
| `ab.notice` | 通知と履歴も関係する | 差戻し理由・通知・履歴を検討 | 変更範囲 |
| `ab.ui` | ボタンは配置できる | 画面上は追加可能 | 技術のみ |
| `ab.api` | APIに変更が必要そう | 実装候補、詳細は未確定 | 技術のみ |
| `ab.ai` | AIの実装案 | 一般的な案、現場確認前 | 参考のみ |

報告に必要な説明要素は `purpose`, `workflow`, `scope` の3つ。
- `purpose`: `ab.pain` + `ab.current` のいずれか、または等価な情報（詳細は実装時に確定）
- `workflow`: `ab.flow` （もしくは同等の再申請根拠）
- `scope`: `ab.state` と、`ab.access` / `ab.notice` のどちらか。**影響範囲が未確定だと認識した説明**で成立させる
- 3枚固定の現行UIを維持する場合、1枚で複数の要素を説明できるよう、上記を報告用カードに再編成すること。生カード3枚では `purpose` に2枚必要など不整合が出るため、実装前に成立可能性をテストする。

### 推奨の報告用3枚（実装しやすいMVP）
`ab.purpose-summary`（三田への確認＋現行フローで解放）、
`ab.return-flow`（再申請経路確認で解放）、
`ab.impact-summary`（状態遷移＋権限または通知で解放）。
これらを **調査.xlsx の手がかりとして追加**する。詳細カードは任意で増やせる。
この3枚が揃えば成功し、技術調査だけでは揃わない。

## 報告の4段階（佐伯は技術判定しない）
- 0: 無関係な実装案・説明にならない → 「すみません、何をおっしゃっているのか、ちょっと分からないのですが……」
- 1: 調査した事実はあるが目的不明 → 「調査いただいたのは分かったのですが、担当者にはどのように説明すればいいでしょうか？」
- 2: 目的と業務フローは説明できるが変更範囲が曖昧 → 「やりたいことは分かったのですが、ボタン一つで済むんでしょうか？」
- 3: 目的・業務フロー・影響範囲が成立 → 主人公が流暢に要件と未確定事項を説明、佐伯「これなら説明できます」
判定は**選択したカード**の説明要素に基づく。所持しているだけでは成立しない。
ただし足りないカードが未入手なら再調査、所持していれば選び直し、という差がリアクションから推測できるようにする。露骨な「不足カードID」表示はしない。

## 報告と時間
- いつでも報告可能。1回10分消費、何度でも再挑戦可。
- 佐伯の機嫌ゲージ・報告回数ペナルティは付けない。
- 時間切れは第1面と同じ途中報告/翌日延長を基本としてまず実装。
- 夢オチ周回・情報持ち越しは今後の拡張候補。**第1面の保存や期限処理を勝手に置換しない**。
- 期限までに完了できなくても、既存のゲームオーバーと再挑戦導線を維持する。

## フレーバー
Slackはゲーム内時刻に連動。1コマンド1投稿にはしない。真壁は別件対応で忙しい。
例: 「差戻しって言うけど、戻した後の担当は誰なんだ」→「仕様書に書いてない」→「俺が書いた仕様書だった」。
真壁の投稿はヒントの補助であり、必須の解法にはしない。

## 非目標
- AIのリアルAPI接続
- ランダム生成案件
- 正解カードのハイライトや正解数ゲージ
- すべての調査を終えることをクリア条件にする
- 正確な工数・納期の断定
