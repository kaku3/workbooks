## 編集とビルド

`01_watermark.md` が編集の正本です。JSONは生成物なので直接編集しません。

`26_report-drill` ディレクトリで実行します。追加パッケージは不要です。

```sh
node scripts/build-content.mjs
node scripts/build-content.mjs --check
```

`--check` はファイルを変更せず原稿との一致を確認します。
Markdownの `##` はJSONのトップレベル項目に対応し、各節のJSONコードブロックを取り込みます。
会話は `### 会話ID (version 1)` の下に `- speaker: 台詞` を記述します。
心の声は `- player [thought]: 台詞` です。第2〜4面の草案は取り込みません。

## JSONの形式
UTF-8のJSON。`schemaVersion` は形式の版、`version` は案件内容の版、`caseId` はシナリオと共通のID。`authorNotes` は作者向けで、画面には出さない。

| 項目 | 内容 |
|---|---|
| `requestMemo` | 調査デスクの初期依頼メモ |
| `clock` | 開始と期限。時刻は同日内の24時間制 `HH:mm` |
| `knowledge` / `intuition` | 初期値・上限 |
| `evidence` | 証拠品。ID、名称、本文、情報源、扱い |
| `investigations` | 調査候補。ID、名称、概要、解放条件、結果分岐 |
| `investigations[].repeatable` | trueなら何度でも時間を使って調べられ、イベント後は未着手へ戻る。同じ結果の報酬は重複させない |
| `outcomes[].complete` | falseなら有用な効果が得られなかった結果として未着手へ戻す。再調査にも時間を使う |
| `questions` | 順番に進める報告の問い・必要枚数・時間・返答条件 |
| `help` | 所持枠、カード、周回ごとの使用上限、結果分岐 |
| `loop` | 持ち越し候補、件数上限、直感の成長量 |

証拠品の `kind` は `confirmed`（確認済み）、`proposal`（提案）、`reference`（参考）。参考情報も提出できるが、成立するかは報告条件で判定する。

## 条件の記法

`unlock` と `when` は次の宣言的な条件で表す。任意コードや文字列の `eval` は使わない。空オブジェクト `{}` は常に成立する。

| 条件 | 意味 |
|---|---|
| `all: [条件, ...]` | すべて満たす |
| `any: [条件, ...]` | いずれかを満たす |
| `evidenceAll: [ID, ...]` | 今回の周回で証拠品をすべて所持 |
| `memoryAny: [ID, ...]` | 指定した記憶を1つ以上持つ |
| `knowledgeAtLeast: {system: 2}` | 指定した知識が下限以上。`business` も指定可能 |
| `intuitionAtLeast: 2` | 直感が下限以上 |
| `flagsAll: [ID, ...]` | 調査結果のフラグをすべて持つ |
| `flagAbsent: ID` | そのフラグを持たない |
| `availabilityIn: [状態, ...]` | 開始時刻の真壁の対応状況がいずれかに一致 |
| `questionIs: ID` | 真壁に聞くときに選んだ質問IDが一致 |
| `selectedAll: [ID, ...]` | 報告で指定カードをすべて選択 |
| `selectedAny: [ID, ...]` | 報告で指定カードを1つ以上選択 |

同じオブジェクトに複数の条件キーがある場合はAND。未知のキーはエラーにし、無視しない。所持カードと報告に選んだカードを混同しない。

## 調査の結果

`outcomes` を上から調べ、最初に一致した1件を採用する。最後は必ず空条件の既定分岐。開始時に結果と消費時間を固定し、確認画面に時間を表示する。

- `minutes`：正の整数の消費分数。
- `scene`：シナリオの会話ID。
- `gain`：業務・システム知識の増加量。省略は0。
- `evidence`：獲得するカードID。重複取得しない。
- `flags`：追加するフラグID。同じ周回では解除しない。

同じ調査の同じ結果IDは周回内に1回だけ効果を適用する。再度同じ結果になる場合は無料再読のみ。条件が変わって未実行の結果IDに変わる場合は、再調査として実行できる。`remembered` 分岐と通常分岐を繰り返すことはできない。記憶は周回中に変わらないためである。

真壁の質問は `questionOptions` に候補を置き、`unlock` を満たすものを表示する。質問選択後に分岐を評価する。説教や会議中の分岐は質問内容より優先する。

ソースの入口のヒントを得ても検証結果は獲得しない。ヒントフラグは表示上の強調に使い、必須の解放条件には使わない。

## 報告

`questions` の配列順に出題する。相手は `to`、問いは `prompt`、必要枚数は `slots`、消費時間は `minutes`。今回の全問は3枚・10分。

1. `reject` の条件を上から調べる。
2. 一致しなければ `accept` を上から調べる。
3. 一致しなければ `fallback` の会話を出す。

`reject` と `fallback` は同じ問を続行、`accept` は次の問へ進行。最後の問が成立したら案件完了へ進む。各会話には主人公が何を報告したか、相手が何を受け取ったかを記載する。

成立条件を追加するときは、3枚で満たせることと、誤解への返答条件に先に捕まらないことを確認する。選択順序は問わない。

## 周回と編集時の確認

記憶は `memoryCandidates` 内で実際に獲得したカードを、定義順に最大 `maxMemories` 件保持する。既存の記憶も候補に含め、新しく得た対象を加える。対象は第1面で3件だけなので獲得済みの記憶を追い出さない。

新しい記憶を1件以上得た周回の終わりに、直感を最大1増やす。「成長済み」の対象IDは全体保存に記録し、案件再開始で直感を稼ぎ直せないようにする。

編集後はJSON構文、IDの一意性、会話・カード参照、条件キー、予定範囲、通常経路の所要時間を確認する。問題の到達条件を変えた場合は、真壁・直感・コーヒーなしでも成立できる経路を再確認する。

`scripts/build-content.mjs` で第1面のMarkdownからJSONと `src/data/content.mjs` を生成する。JSON・実行データは直接編集しない。第2〜4面のMarkdown草案は対象外とする。
