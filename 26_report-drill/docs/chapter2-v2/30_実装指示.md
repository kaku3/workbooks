## 重要な構造上の差
添付版は `scripts/build-content.mjs` が `01_watermark` 固定で、`src/data/content.mjs` に単一ケースを出力する。
`docs/problems/02_approval-button.md` / `docs/scenarios/02_approval-button.md` は今のところ文章草案。
第2面追加には「シナリオ/問題のデータ化」と「実行ケース切替」が必要。

## 実装フェーズ
### Phase 1: ケース切替基盤
- 第1面の現行動作を維持。
- 第2面の `caseId=approval-button` を読み込めるデータ構造を導入。
- ビルドはケース単位でMarkdown正本→JSON→ランタイム生成。生成物を手編集しない。
- ケース別セーブキー（既存 `report-drill.pdf-incident.v1` を保持）。
- 第1面のクリア後に第2面へ進める、またはデバッグで直接第2面を開ける導線。
- 現行UI・設定・履歴・調査.xlsx・会議画面は共通化して再利用。

### Phase 2: 調査と報告
- 導入に「目的→必要な修正範囲→見積もり根拠」の主人公独白を追加。案件概要からも判断軸を再確認できるようにする。
- 報告は金額確定ではなく、安価なボタン追加見積もりでは済まない理由を説明する一次報告とする。
- `10_第2面仕様.md` の調査カード・証拠品・依存関係を実装。
- 「技術調査を続けても情報は増えるが、報告に必要な要素が揃わない」を再現。
- 報告3枚選択UIを維持。3枚の要約証拠 `purpose-summary`, `return-flow`, `impact-summary` を生成できるようにする。
- 成立判定は選択カードの説明要素に依存し、所有枚数だけでは判定しない。
- 不成立報告は選択を保持して再挑戦できる。1回10分消費。
- 成立時は主人公の説明→佐伯の返答→案件完了。
- 調査の解放・所要時間短縮があれば既存の演出を再利用。

### Phase 3: 物語と期限
- `40_台詞原稿.md` を案件専用シーンに落とす。
- 真壁/佐伯/三田の話者IDは既存の人物定義に合わせる（現行第1面では佐伯=`client`、真壁=`lead`）。
- Slack投稿は時刻連動で複数表示される。
- 途中報告・延長・期限切れは既存の規則を維持。
- 第2面で夢オチ/周回持ち越しを追加するなら、別フェーズで仕様を確定してから実装。

## 受け入れテスト（最低限）
1. 第1面を従来どおり開始・続きから・完了できる。
2. 第2面を新規開始すると第1面のセーブを破壊しない。
3. 画面仕様→ソース→API→UIだけでは報告成功しない。調査カードは有益な結果を返す。
4. 三田→現行フロー→再申請では、目的/フローの報告はできるが影響範囲が不足する。
5. 三田→現行フロー→再申請→状態→権限で報告が成立する（実際の解放条件に合わせて調整）。
6. 代替経路として「状態→通知」でも報告が成立する。
7. 実装方式の比較を実行しなくても成功する。
8. 不成立報告を繰り返しても佐伯の機嫌は悪化せず、毎回10分経過する。
9. 不成立後、選択カードを維持し調査に戻れる。
10. 期限直前の調査/報告で18:00を越えたら、結果を付与する前に既存期限処理へ進む。
11. 途中報告済みなら翌日へ一度延長され、証拠・履歴が引き継がれる。
12. Slackの投稿はゲーム内時刻に従い、長時間調査後は複数まとめて届く。
13. `npm run build`, `npm test`, `node scripts/build-content.mjs --check` を通す。
14. 導入独白を読めば調査終了の判断軸が分かるが、正解チケットや必要カードは露出しない。
15. 未着手チケットが残っていても報告成功できる。
16. 可能なら `npm run test:browser` とスクリーンショットでUI確認する。
