# 第3章 セリフのリライト方針

## 1. 今回やりたいこと

[第1章](../scenarios/01_watermark.md)・[第2章](../scenarios/02_approval-button.md)のリライトに合わせて、[第3章の会話原稿](../scenarios/03_bulk-import.md)を全面的に見直す。

調査結果を順番に説明するだけでなく、主人公が「これなら簡単そう」と思い、実際に触って面倒なことに気づき、相手に説明しても思ったように伝わらない。その一日のやり取りとして読めるようにする。

今回はそのための方針整理。セリフ本文の書き換えや、調査フロー・クリア条件の変更は次の作業に分ける。

## 2. 1章・2章から引き継ぐ調子

### 調べた事実に、主人公の都合が混ざる

第1章の「俺が印刷しても田中太郎じゃん」、第2章の「却下ボタンをコピペしてラベルを変えれば」のように、主人公は立派な調査担当として考え続けてはいない。早く終わりたいし、面倒な修正は増やしたくない。分かったことを、自分に都合よく受け取る瞬間がある。

第3章でも、CSVを読んで既存APIを繰り返せば終わると思いたい。メールや二重登録を見つけるたびに、見なかったことにしたくなる。ただし、調査した事実まで曖昧にせず、心の声との落差で人物を出す。

### 会話の相手は、主人公と同じものを見ていない

第2章では、主人公が差戻し後の使い方を説明して、佐伯が初めて便利さに気づく。同じ依頼を扱っていても、開発側と窓口と実際の利用者では、気にしていることが違う。

第3章では、主人公は作る手間、佐伯は担当への返事と費用、実際の担当者は毎朝の入力とやり直し、折原は受注額を気にしている。「一括登録」という言葉だけで話が通じたつもりになるところから、この違いが見えるようにする。

### 笑いは、仕事をしている途中で出る

自分にも覚えがある愚痴、言い訳、過去の失敗、どうでもいい持論を混ぜる。真壁も、いつも適切な助言を短く返す先輩にはしない。話が脱線したり、自分の失敗を思い出したりする。

「死んだばーちゃん」「俺が書いた」「10万円」など、既存の小ネタは使える。ただし、全場面にオチを付けたり、前章のネタを繰り返すだけにしたりしない。短い事実確認や沈黙の場面も残す。

## 3. 第3章で描く話

**「まとめて登録するだけ」のつもりが、失敗した後の仕事まで考えることになる。しかも、作る側が楽な方法と、使う側が楽な方法は同じではない。**

章全体の流れは、次のように捉える。これは執筆上の流れで、プレイヤーの調査順を固定するものではない。

| 段階 | 主人公の受け止め方 | 会話で見せたいこと |
|---|---|---|
| 依頼を受ける | CSVでまとめればいけるのでは | 佐伯の伝聞と、折原の10万円だけが先に進む |
| Excelと画面を見る | コピペが減るなら喜ばれそう | 列順・数字・日付の補正は、今も誰かがやっている |
| 既存処理を調べる | APIを繰り返せば済みそう | 登録だけでなく関連データや通知も動いている |
| 試作・追跡をする | 止まったら戻せばいいのでは | 先に成功した登録やメールが残る。入れ直すと重複する |
| 方法を考える | 全部戻す方が作りやすそう | 担当者には、全部入れ直す仕事が残る |
| 概算を比べる | 便利にすると10日もかかるのか | 手間を減らすために、結果管理や再投入対策が増える |
| 報告する | 調べた内容を言えば通じるはず | 相手が知りたいのは、自分たちの仕事と費用がどう変わるか |
| 持ち帰ってもらう | ひとまず回答できた | 両案の違いが伝わり、利用部署で相談できる状態になる |

「全部戻すのが正解」「便利な方を作るのが正解」という結末にはしない。どちらにも残る仕事があり、その違いを理解してもらうところを着地にする。

## 4. 人物ごとの書き方

人物像は[キャラクター設定](../characters/README.md)に従う。

| 人物 | 第3章での関心 | セリフの方向 |
|---|---|---|
| 主人公 | 無事に見積もりを返して一日を終えたい | 最初は流用やコピペに期待する。調べるほど面倒が増え、心の声では愚痴るが、対外的には確認して説明する |
| 佐伯 | 担当に返事をしたい。費用を増やしたくない | CSVや内部処理の説明には乗り切れない。何を用意するのか、なぜ金額が増えるのか、自分が持ち帰れる言葉で聞き返す |
| 折原 | 10万円の話を進めたい | 工数より金額が先に出る。途中や報告で短く反応させてもよいが、技術的な可否や正式価格は決めさせない |
| 真壁 | 自分の仕事も片づけたい。後で揉めるのは避けたい | 経験談や実務上の都合から話す。マクロ案や失敗談は出すが、今回の現場を知り尽くした先生にはしない |
| 登録担当者 | 毎朝の転記を減らしたい。やり直しも増やしたくない | 列や表記の補正を日常作業として捉えている。全件やり直しと失敗分だけの修正では、受け止め方が違う |

登録担当者の情報は、現行原稿の佐伯経由の回答を基本にする。人物を直接出すためだけに、担当者を三田と決めたり、新しい所属・役職を追加したりしない。

主人公の心の声には多少の悪意や早合点があってよい。ただし、それを作品の結論にはしない。「使うの俺じゃないし」で済ませたくなっても、実際の手間を聞けば話が変わる余地を残す。

## 5. 現行原稿で活かすところ・直すところ

すでに第3章にも、1章・2章に近い調子のセリフがある。全面的に見直すが、良い場面まで別物にする必要はない。

### 活かすところ

- `03.intro` の、主人公が出したCSVという言葉に佐伯が乗るやり取り。方法が決まっていないのに話が進む導入になっている。
- `03.screen` の「チョロい？」から、試作で止まって困る流れ。
- `03.makabe-macro` の、真壁にとっては当たり前のExcelマクロが主人公には思いつかないやり取り。
- `03.makabe-incident` の「メール100通」「俺が」という失敗談。
- `03.estimate-both` の、自分で積んだ10日に自分で驚く反応。
- `03.report-3` の、折原がもう見積書を開いている締め。

### 優先して直すところ

- **説明文が続く調査場面。** 「確認した」「必要がある」だけで閉じず、主人公が何に期待し、どこで嫌な予感がしたかを入れる。ただし毎回「面倒くさい」で終えない。
- **一度に話が片づく確認場面。** CSV準備や対象範囲の合意は、相手が何をするのか確かめる応酬にする。長い説明一回で双方が全部理解したことにしない。
- **最終報告。** 現行の主人公の連続説明を、佐伯の疑問と反応を挟む会話にする。調査結果の読み上げから、相手が理解して持ち帰れるやり取りへ変える。
- **真壁の長い助言。** 役立つ内容は残しつつ、正論をまとめて教える形を減らす。今回を知らないところ、自分の都合、会話が切れる間も使う。
- **チャットの教訓。** 「顧客に決めてもらう話と、こちらで決める話」などの持論は、仕事中の独り言として馴染ませる。攻略の説明が一定間隔で届くようにしない。
- **表記上の混乱。** `03.mapping` の `player: player:` は修正する。「２～３０件」は「20〜30件」に揃え、件数を誤読させない。強調と改行は、驚きや会話の間に必要な箇所へ絞る。

## 6. 場面別の修正方針

以下のシーンIDはすべて `03.` を付ける。

| 場面 | 主なシーン | 修正の方向 |
|---|---|---|
| 導入・依頼 | intro / request | 手入力を減らしたいという話と10万円が先に来る。最初から失敗時の設計課題や両案を説明しない。回答期限も会話内で分かるようにする |
| 業務と現物 | business / workbook / mapping | 実際の作業、ファイルで見えた違い、入力して初めて分かったことを分ける。面倒な補正を誰が今やっているのかに気づく場面にする |
| 準備と運用 | csv-preparation / csv-preparation-first / operations | 「CSVにすれば終わり」と「CSVを作る人の仕事」のずれを描く。全件再投入の負担を聞いても、その場で採用まで決めない |
| 既存処理 | screen / source / spec / related / notification / retry | 使い回せそうという期待から、確定・通知・重複という具体的な引っかかりへ進む。専門語だけで説明しない |
| 試作の結果 | prototype / related-prototype / notification-prototype / notification-followup / retry-prototype | 止まった、残った、届いた、増えたという観測と反応を中心にする。既存処理を読んだだけの場面とは言い分ける |
| 処理案と概算 | plan-a / plan-b / plan-both / estimate-a / estimate-b / estimate-both | 作る側の手間と使う側の手間が逆方向に動くところを見せる。1日と10日は同じCSV前提の概算として説明する |
| 根拠不足 | estimate-missing / estimate-missing-structure / estimate-missing-notification / estimate-missing-retry | まだ分からない一点に引っかかる独白にする。既に調べたことを忘れたり、調査手順を全部読み上げたりしない |
| 相談 | makabe-* | 今回の質問と真壁の関心が噛み合う時も、噛み合わない時も描く。マクロの提案と、今回それが用意できるかの確認は分ける |
| 途中報告 | progress-* / report-progress / report-cannot | 確認できたことと残りを短く話す。真壁への連絡と佐伯への説明では、話す内容と口調を変える |
| 不十分な報告 | report-0 / report-csv / report-only-a / report-only-b / report-operation | 採点の講評ではなく、相手が判断できずに聞き返す場面にする。Aのみなら真壁が担当の負担を問い、Bのみなら佐伯が費用に難色を示す |
| 最終報告・完了 | report-3 / clear | 相手の疑問を受けて、準備、やり直し、工数差を説明する。佐伯が利用部署へ持ち帰り、主人公はひとまず肩の荷が下りる |
| 寄り道・再確認 | summary / libraries / distributed / tables / macro-check / detail / recheck / no-progress | 調べた成果がある寄り道と、同じところを見た空回りを区別する。調査を切り上げたい気持ちも出す |
| 休憩・期限・翌日 | lunch / coffee / timeout / extension / gameover / extension-used / next-day / dream | 前章の温度感に揃える。期限超過で問題になるのは、途中で状況を伝えず抱え込んだこととして描く |
| 社内チャット | chat | 真壁自身の一日を見せる。短い投稿、仕事の経過、持論、どうでもいい話を混ぜ、全部を案件のヒントにしない |

## 7. 最終報告は、説明を聞いて相手の認識が変わる場面にする

第2章の成功報告のように、相手の理解が進むところを会話の中で見せる。第3章では、次の順に話題を組み立てる。

1. まず、減らすのは画面への一件ずつの転記だと説明する。
2. 「Excelを渡せば全部やってくれるのか」という疑問に、担当が列や表記を揃える前提を伝える。この準備方法は担当と確認済みであることも添える。
3. 全件取消なら概算1日、と示す。エラーがあれば成功分も残らず、直して全件を入れ直すことをセットで伝える。
4. 「通った分を残せないか」に、失敗分だけやり直せる案は概算10日と返す。何が成功したかの記録や、入れ直した時の二重登録を防ぐ作業が増えると説明する。
5. 佐伯が、早く作れる方法とやり直しを減らす方法の違いを理解する。詳細を詰める前の概算であることを伝え、両案を担当部署で検討してもらう。

この順番は台詞化のたたき台。長い問答にせず、佐伯が気にする箇所で短く聞き返し、主人公が答える形にする。実際の作業を減らせる期待と、10日という数字への抵抗の両方を残す。

口調の方向例（採用確定のセリフではない）：

> 佐伯：まとめて入れられるなら、今のExcelを渡せばいいんですよね？  
> 主人公：列の順番や日付は、担当の方で揃えてもらいます。今回は、画面に一件ずつ入力するところをなくす見積もりです。  
> 佐伯：なるほど。直す作業は残るんですね。

> 佐伯：通った分だけ残すと、10日ですか？  
> 主人公：はい。どれが通ったか分かるようにして、やり直した時に同じものを二回登録しない仕組みも要るので……。  
> 主人公 [thought]：作る前は、俺も繰り返すだけだと思ってたんだけど。

成功しても、その場でA案・B案を採用したり、10万円で受注したりはしない。佐伯が説明できる状態になり、持ち帰ってもらえれば、この章の仕事はいったん終わる。

## 8. セリフを変えても維持する事実と分岐

判断の根拠は、[背景](background.md)・[第3章仕様](10_第3章仕様.md)・[問題データ](../problems/03_bulk-import.md)に合わせる。[implementation.md](implementation.md)などの旧資料から、確定工数や採用決定を戻さない。

- 既存機能は単件登録。一括登録の完成版はまだない。試作で見た失敗を、稼働中の一括機能の不具合として語らない。
- ソースから分かったことと、検証環境で実際に起きたことを言い分ける。未選択の調査でしか分からない事実を、セリフに先回りして入れない。
- 普段20〜30件、月初50件、約6項目。取引先Excelは列や表記が揃っていない。
- 担当が所定CSVを準備する前提で、全件取消は1日程度、正常行を残す方法は10日程度。詳細設計・全試験が終わった確約にはしない。円換算の単価も新しく設定しない。
- Excel自動変換やマクロ新規開発は、この概算とは別範囲。真壁が案を出しただけで、マクロが存在・完成したことにはしない。
- A案のみの報告、B案のみの報告、業務の確認が足りない報告は、それぞれ不足する視点が伝わる反応を維持する。
- 同じシーンに入れる条件を確認する。例えば一案の報告では、もう一案を未調査と決めつけず、「別のやり方はないか」と問い直す。知っているのに忘れた会話を作らない。
- `plan-both`・`estimate-both` は旧保存の表示用。現在の進行で両案を一度に取得する経路として復活させない。
- 真壁相談・片案報告・チャット閲覧を必須にはしない。会話を面白くするために解放条件や所要時間を変えない。
- 成功は、両案と業務への影響を佐伯が理解して持ち帰るところ。採用判断、正式見積もり、実装は次の仕事として残す。

## 9. 実際にリライトする時の進め方

1. **導入と成功報告から書く。** 最初の思い込みと、最後に伝わる内容を揃える。折原の10万円も、章の始めと終わりで効くようにする。
2. **一案のみ・業務不足の報告を書く。** 相手の疑問を具体化し、成功報告との差を作る。
3. **調査と相談を書く。** 発見を残しながら、主人公の期待、愚痴、驚き、迷いを場面ごとに変える。既にある良い台詞を活かす。
4. **途中報告・期限・休憩・チャットを揃える。** 第1章・第2章と続けて読んだ時に、人物の口調と一日の空気が繋がるか確認する。
5. **各分岐から読む。** ソース中心と試作中心、CSV準備を先に聞く経路、A/Bそれぞれの片案報告から読み、未調査の事実や既知情報の忘却がないか確認する。

編集正本は `docs/scenarios/03_bulk-import.md`。既存のシーンIDと話者IDを維持し、変更したシーンの版を更新する。JSON・`content.mjs` は手編集せず、本文のリライト後に既存のビルド手順で生成し、分岐と表示を確認する。

## 10. リライト後の確認点

- 調査結果だけを追っても、何が分かったか読み取れるか。
- 心の声を読むと、主人公がその仕事をやりたくない理由や期待が見えるか。
- 佐伯・真壁・折原が、それぞれ自分の都合で話しているか。
- 同じ「面倒」「分からない」「調べよう」で毎回閉じていないか。
- 相手の疑問と返答によって会話が進み、説明文の分割だけになっていないか。
- 冗談を読まないと重要な条件が分からない構成になっていないか。
- 1日と10日の差だけでなく、担当に残る準備とやり直しの違いが伝わるか。
- 未完成の機能や概算を、確認済み・約束済みとして語っていないか。
- 成功報告で、相手が何を理解できたのか、その反応から分かるか。
- 読み終わった時に、模範解答を覚えた感じより、面倒な依頼にひとまず返事ができた感じが残るか。
