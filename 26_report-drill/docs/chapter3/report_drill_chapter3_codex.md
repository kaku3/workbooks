## 1. この面で体験させたいこと

第1面：調査すれば原因が分かる。
第2面：業務目的と修正範囲を確認し、見積もりの根拠を説明する。
**第3面：技術的に調査し尽くしても、顧客の業務判断が必要なことがある。**

ゴールは「正しい実装方式を当てる」ことでも「B案の調査工数を詰める」ことでもない。**A案・B案の違い、業務への影響、工数を整理して佐伯に提示し、どちらを選ぶか判断を仰ぐこと**。顧客がA案を選んでもB案を選んでもプレイヤーの正誤には関係しない。どちらかを独断で決定する報告は不十分。

プレイヤーが早い段階で気づいて報告してもよいし、チケットをすべて調べた後で気づいてもよい。真壁への相談は救済・発見経路の一つであり、必須フラグにしない。

## 2. 案件の事実（第3面の前提として確定）

佐伯から「毎朝の手入力を減らしたいので、CSVでまとめて登録したい」という依頼。登録担当部署では、正常な行だけでも先に処理できると便利だが、コストと優先度はまだ判断していない。現行の単件登録には入力検証、関連データ更新、通知があり、CSV化にはエラー時の扱いと再投入時の重複対策が関係する。

比較する方式は次の2案に固定する（ゲーム内での案件固有の見積もりであり、一般論ではない）。

| | A案 | B案 |
|---|---|---|
| エラー時 | 1行でもエラーなら、そのファイルの登録を全件取り消す | 正常な行だけ登録し、失敗行を区別して返す |
| 業務メリット | 結果が単純、導入が早い | 正常行の再入力を避けられる |
| 業務上の負担 | エラー修正後にファイル全体を再投入 | 成功・失敗の区別と再投入の運用が必要 |
| 実装工数 | **1日** | **10日** |
| 技術的な見通し | 実現可能、見積もり確定 | 実現可能、見積もり確定 |

**重要：B案の工数は最終的に確定してよい。** 「10日かかると分かっても、顧客の判断なしに着手できない」が学習ポイント。追加調査を無限に要求したり、「B案の工数が分からないから相談する」という別テーマにすり替えない。

A案が絶対的な正解という扱いもしない。B案を選ぶだけの業務価値がある可能性もある。費用対効果と運用を踏まえた判断は佐伯／依頼部署の役割。

## 3. 既存UIでの体験設計

**新しい「途中相談カード」「相談ボタン」「攻略ヒント表示」は作らない。** 既存の調査カンバン、調査.xlsx、チャット、真壁への途中報告、Meets報告を再利用する。報告タブの名称変更だけで行動を誘導しようとしない。

- 調査カンバン：CSV形式、対象件数、現行登録処理、エラー処理、再投入、A/Bの見積もりなど、調査対象を自然な仕事の粒度で配置。意味のある寄り道（CSVライブラリ比較、大規模分散構成、対象外のテーブル調査等）も残す。
- 調査.xlsx：各方式の事実を証拠として蓄積。単一の「A/B案を顧客に相談せよ」カードは作らない。プレイヤー自身が比較して判断を仰げるようにする。
- Meets：最終回答だけの場に見えても、プレイヤーが自主的に「現時点の案を提示し、方針を決めてもらう」報告をできるようにする。適切なカードの組み合わせで成功。早期の成功も許す。
- チケットを全部終えても、自動的にA案／B案が決定することはない。残チケットの有無をクリア条件にしない。

### 証拠の設計

少なくとも次の事実を**別々の調査結果**として得られるようにする。
1. 業務目的：手入力削減。途中失敗時の運用が重要。
2. A案：全件取り消し、1日。メリット・制約。
3. B案：正常行を残す、10日。メリット・制約（関連更新、通知、重複防止の確認を経て確定）。

必要な事実をカード3枚程度で報告できる構成を優先し、既存の3枚選択UIを維持する。具体的な証拠IDや採点条件は現行エンジンの仕様に合わせて設計する。技術的に詳細な調査をすべて終えることは必須にしない。ただし「B案10日」の根拠に到達するための必要な調査は設定する。

## 4. 真壁の社内チャット強化

真壁は「仕事の持論を語るのが好き」な人物として、案件と無関係な雑談・ちょっと役立つ話・微妙な話を**同じ温度感で**流す。攻略メッセージを色や表示位置で特別扱いしない。第1・2面のチャットとの整合も確認し、必要なら自然な範囲で補強する。

第3面のヒントとして、例えば以下を時刻順の投稿に混ぜる（原稿は適宜推敲）。

- 「結論を一つにまとめられないときは、現状の案を整理して顧客に相談するのも手だ。」
- 「まあ、選択肢を整理するのが一番面倒なんだけどな。」
- 「ちなみに何でも顧客に決めてもらえばいいって話じゃないぞ。技術的なことまで丸投げするなよ。」
- 「会議で一番長く喋ったやつが議事録書けばいいと思うんだよな。」

**チャットを読まなくてもクリア可能**とする。チャット閲覧自体で証拠や知識、正解フラグを与えない。既存の時刻連動の投稿方式を守る。

### チャット新着の視認性（追加要件）

**新しい投稿があったことは目立たせる。ただし、ヒントを含む投稿だけを目立たせない。** 既存UIのレイアウトを大きく変えず、チャットの未読状態を分かりやすくする。

- チャットを閉じている間に投稿が増えたら、チャットタブ／入口に未読ドットまたは未読件数を表示する。重要そうな投稿だけでなく、雑談を含む**すべての新着投稿を同じ基準**で扱う。
- 新着時はタブに控えめな一度きりの強調アニメーションを付けてよい。常時点滅・繰り返し揺れ・画面を遮るポップアップ・音は使わない。動きを減らす設定にも配慮する。
- チャットを開いたら、未読の開始位置が分かるようにする（未読区切り表示やスクロール位置など、既存のスクロール仕様に合う最小実装）。未読解除のタイミングは「開いた時／表示した時」のいずれかに統一する。
- ヒント投稿にだけ専用色・アイコン・強調・固定表示を付けない。**新着通知は入口への誘導であって、正解への誘導ではない。**
- 既存の投稿時刻・時間経過・保存／再開との整合を確認する。再開時に過去の投稿が一斉に新着扱いされないようにし、必要に応じて既読状態を保存する。
- 第1・2面でも同じ通知ルールを使い、第3面だけ突然チャットが特別扱いされないようにする。
- チャット未読のままでもクリア可能であることは維持する。


## 5. 真壁への途中報告：収集情報で反応が変わる

既存の「真壁への途中報告」は、期限延長にも関係する機能。**既存の延長条件・時間消費・進行を壊さず、会話だけを調査状況に応じて変える**ことを基本にする。途中報告と佐伯へのMeets報告を混同しない。

例：

| 情報の段階 | 真壁の反応例 | 狙い |
|---|---|---|
| まだ方式比較がない | 「で、何が分かったんだ？ CSVで読める、だけじゃないよな」 | 失敗時の扱いへ視点を広げる |
| A/Bの違いは把握、工数の裏付けが弱い | 「二通りあるんだろ。何が違って、どこに工数がかかるんだ？」 | 比較可能な材料を揃える |
| A=1日、B=10日まで判明 | 「で、どっちにするんだ？ ……それ、お前が決めることか？」 | 判断者が違うと気づく |
| 必要な材料を十分に把握 | 「選択肢と影響を整理して持っていけよ。調べ終わるまで黙ってる必要はないぞ」 | 相談・報告へ背中を押す |

台詞は具体的な正解カード名や手順を列挙しない。情報段階は「所持している証拠・調査済みフラグ」で判定し、チケットの消化数だけで判定しない。**相談を経由しない最短クリアも成立**させる。真壁の忙しい時間・質問の具体性に応じた既存リアクションも維持し、無条件に教える万能ヒント係にしない。

## 6. Meets報告の反応とクリア条件

既存の報告形式に合わせ、報告内容の不足を佐伯の自然な問い返しで伝える。採点画面や「正解カード」の直接提示は不要。

- CSVで登録できることしか伝えない：佐伯「読み込めるのは分かりました。途中でエラーになったらどうなりますか？」
- A案だけを推奨する：佐伯「早いのは助かります。でも、途中で一件間違っていたら、全部やり直しですか？」
- B案だけを推奨する：佐伯「便利そうですが、1日と10日ではだいぶ違いますね。もっと簡単な方法はないのでしょうか？」
- A/Bの比較はあるが業務への影響がない：佐伯「それぞれ、担当部署の作業はどう変わりますか？」
- A/Bの方式・運用上の違い・工数が整理され、判断を仰ぐ：**クリア**。

成功会話案：

主人公「一括登録には二つの方法があります。A案はエラーが一件でもあれば全件取り消しで、1日です。B案は正常な行を登録して失敗行を分けられますが、10日かかります。」
主人公「運用の手間と費用が大きく変わります。どちらで進めるか、担当部署とご判断いただけますか？」
佐伯「なるほど。まずはA案でも助かるか、登録担当に確認します。10日かける価値があるかも含めて判断します。」
主人公［心の声］「全部調べても、俺が決めることじゃなかったのか……。」

佐伯が必ずA案を選ぶ結末に固定しない。**「顧客が判断するための材料が揃った」時点でクリア**。報告失敗後は調査に戻って再報告できる既存仕様を維持。

## 7. 時間設計と寄り道

A/Bの工数が分かる標準経路は、既存の締切と途中報告の延長を使って無理なく到達可能にする。チャット未読・真壁未相談でも達成可能な経路を用意する。余計な調査を続けると期限が厳しくなるが、気づく前に必ず時間切れになるような罠にはしない。

寄り道は単なる無意味なハズレにしない。CSVライブラリ比較や大規模構成の検討も技術的には正しいが、「今回どちらの運用を選ぶか」を決める材料としては優先度が低い、という作りにする。

## 8. 実装手順

1. 現行の第1・2面実装、ケース選択、ビルドスクリプト、保存、途中報告、報告判定、チャット表示を調査。既存仕様との差分を整理する。
2. `docs/problems/03_bulk-import.md` を現行スキーマに沿って正式な問題原稿へ。案件事実、証拠、調査タスク、解放条件、時間、報告判定を実装。
3. `docs/scenarios/03_bulk-import.md` を正式なシナリオ原稿へ。導入、調査、真壁の段階別反応、佐伯の報告反応、成功・失敗、チャット、予定を記述。
4. 必要な場合だけエンジンに「証拠・調査フラグによる途中報告の会話分岐」を追加。第1・2面の既存分岐と互換にする。
5. 現行ビルド方式で生成・検証し、第3面が選択・再開できるようにする。新UIは原則追加しない。
6. 自動テスト・手動プレイで検証し、実装差分と未解決点を報告する。

## 9. 受入条件（必須）

- A案1日・B案10日が調査結果から確認できる。B案の工数が不明なまま終わらない。
- 両方式の業務上の利点・制約を示し、顧客に選択を仰げばクリアできる。
- A案またはB案をプレイヤーが独断で選ぶだけではクリアしない。
- 真壁に一度も相談せず、チャットも読まずにクリア可能。
- 真壁への途中報告の台詞が収集した情報によって変わる。期限延長など従来の効果は維持。
- チャットは通常の雑談と持論にヒントが混ざる。特別なヒントUIを設けない。
- 新着チャットが未読ドット／件数などで視認でき、開くと未読位置が分かる。雑談とヒントの通知基準は同一。既読・保存・再開が破綻しない。
- 全チケット消化をクリア条件にしない。早めに適切な報告をしてもクリアできる。
- 不十分な報告後、調査に戻ってやり直せる。
- 第1・2面のシナリオ、保存、時計、期限延長、会話表示に回帰不具合がない。
- Markdown正本→生成→チェックの既存開発フローに従う。関連テストを追加する。

## 10. 判断に迷った場合の優先順位

1. **「調べれば分かる」と「誰が決めるか」は別**という体験を優先する。
2. 既存UIとゲームルールを極力維持する。
3. ヒントはチャットと人物の反応に溶かし、正解ルートを直接教えない。
4. 1日／10日はこの案件の前提値。実務一般の相場として扱わない。
5. 追加機能が必要なら先に影響を説明し、最小変更で実装する。
