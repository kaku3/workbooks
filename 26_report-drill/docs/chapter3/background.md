# 第3章「一括登録機能」背景・要求の掘り下げ

> **状態：再設計をゲームへ反映済み。** 問題・会話の編集正本は docs/problems と docs/scenarios。調査の構造と背景は本分冊を参照する。

資料の入口は [00_README.md](00_README.md)。このファイルは、なぜこの依頼が来たか、何をまだ知らないか、既存システムと新規機能の境界を固定する。調査の順序と所要時間は [20_フロー.md](20_フロー.md) に分ける。

## 1. 依頼が生まれた背景

取引先から届いたExcelを見ながら、担当者が毎朝、社内システムへ一件ずつ入力している。目的はこの手入力を減らすこと。CSVは主人公が考えた実現方法の候補であり、依頼者が確定した仕様を持ち込む話ではない。

依頼者の言葉だけでは、転記が遅いのか、表記の補正が重いのか、入力後の確認に時間がかかるのかは分からない。入力件数だけで負担を判断せず、現物と担当者の作業から調べる。折原の10万円という話も、合意済み予算や開発側の見積もりとは扱わない。

## 2. 要求を掘り下げる観点

| 観点 | 設計上の背景・確認すること | まだ決め付けないこと |
|---|---|---|
| 誰のどの仕事を減らすか | 登録担当者の朝の転記。表記補正や結果確認も含めて現在の手順を見る | ファイルを読めば全ての負担がなくなるとは限らない |
| 件数・頻度 | 普段20〜30件、月初50件ほど。約6項目を毎朝入力 | 佐伯の数十〜百件という伝聞を実績にしない |
| 入力元 | 取引先ごとに列順・書式が異なるExcel。全角数字や日付を担当が直している | 最初から所定CSVが届いていることにしない |
| 入力を誰が整えるか | 担当が用意できる形式と残る手間を、見本で確かめる | マクロが既にある、または開発側が無償で新しく作ると決めない |
| エラー時の仕事 | 全件を入れ直す場合と、失敗行を区別して直す場合の手順・負担を考える | 利便性が高ければ費用を問わず採用されるとは限らない |
| 依頼範囲 | 所定CSVを受け取る登録部分と、Excel自動変換・マクロ新規開発を分ける | 自動変換の希望をなかったことにせず、追加範囲として残す |
| 工数の扱い | 一日の調査では詳細設計・全試験は終わらない。大きな作業差を概算する | 1日／10日を実装検証済みの確約や一般相場にしない |
| 誰が判断するか | 開発側は実現方法・負担・概算・留保を示し、佐伯が部署で検討する | 主人公や真壁が便利さと費用の釣り合いを代わりに決めない |

### 比較のために確認する共通条件

A案・B案の1日程度／10日程度は、担当部署が列・数値・日付を整えた所定CSVを用意し、システムがそれを検証・登録する範囲の概算。取引先Excelの自動変換、あらゆる表記揺れの自動補正、マクロ新規開発は含めない。不正な形式を黙って受け入れるという意味でもない。

この共通条件は設計者が持つ比較の枠組みで、プレイヤーが最初から知る仕様ではない。Excelと入力項目を比べ、担当者と準備方法を試す中で確認する。人手の前処理を今後も採用することまで発注決定したわけではない。

## 3. 業務・人物・現行システムの前提

### 3.1 設計者が固定しておく現場

取引先ごとに書式・列順の違うExcelが届く。担当者は商品コード、商品名、数量、単価、納品予定日など約6項目を見て、全角数字や日付表記を直しながら単件画面に転記している。普段20〜30件、月初は50件程度。

現在の流れは次の通り。

```mermaid
flowchart LR
  X[取引先ごとのExcel] --> H[担当者が表記を直す]
  H --> S[単件画面に転記]
  S --> V[入力検証]
  V --> D[登録と関連データ更新]
  D --> N[通知]
```

入口でExcelを自動変換するか、人が整えたCSVを受け取るかは、依頼時点では未確定。最終的な1日／10日の比較は、調査の途中で**担当部署が所定CSVを用意する範囲に絞った場合の見積もり**として成立させる。

### 3.2 各人物が最初に知っていること

| 人物 | 知っていること・関心 | まだ知らないこと／発言の限界 |
|---|---|---|
| 登録担当 | 実際の件数、Excelの癖、日付や数字を直す手順。朝の転記を減らしたい | 自分の補正が実装範囲に影響すること、取込後の整合・通知の仕組み |
| 佐伯 | 朝の入力が負担だという相談を受けた。部署に返事をしたい | 正確な件数、入力補正、何を自動化するか。現行原稿の百件という見込みは伝聞扱いで、実績確認後に訂正する |
| 折原 | 受注と金額を早く進めたい | 実装範囲と工数。10万円という発言は承認済みの予算や見積もりではない |
| 主人公 | 画面・ソースを調べ、CSVでまとめる方法を考えられる | 担当者の暗黙の作業、現行登録の副作用、業務側が許容する運用負担 |
| 真壁 | 過去の一括処理、マクロでの前処理、再送の失敗などの経験 | 今回の担当者の道具・手順・優先度。マクロの存在や利用部署の希望を代わりに確定できない |

業務情報は担当者との確認、実物の情報はファイル、処理の情報は画面・コード・実行記録から得る。佐伯や真壁に、その時点で知り得ない情報を一括で説明させない。担当者の情報を直接登場で伝えるか、佐伯経由の回答や作業メモで伝えるかは、構造の確認後に台詞制作で決める。

### 3.3 再設計案で固定する技術上の事実

**既存なのは単件登録だけで、一括登録・ファイル単位の取消・行別の結果返却・CSV再投入の処理は、今回これから作る。** 既存ソースや既存テストに完成済みの一括処理があることにはしない。以下は、この章の架空の単件登録についての設定であり、現実のリポジトリにその業務システムが実装されているという意味ではない。

- 単件登録は一回の呼び出しで登録と関連更新を確定し、その後に通知する。ソースと単件テストで、この一件分の境界と順序を調べられる。
- 同じ単件入力を二回送った場合の登録IDや通知を調べられる。ただし、その結果だけで未実装のCSV再投入の挙動を確認済みにはしない。
- P1では、既存の単件処理を数回呼ぶだけの小さな検証用コードを新しく用意する。この試作を止めた後に先の呼び出し分が残ることは観測できるが、完成版の一括登録の不具合ではない。
- 関連更新は同じデータベース内にあり、全件取消案ではトランザクション境界や通知の呼び出し位置を変更する見通しを立てる。まだその変更を実装・検証済みではない。
- 正常行を残す案では、行別結果・再投入の識別・通知重複対策などを新規に設計する必要がある。どこまで既存処理を流用できるかを調べ、作業量の違いを考える。

| 区別 | この章での扱い |
|---|---|
| 確認した事実 | 単件処理の入力検証・確定単位・関連更新・通知、担当者の仕事、P1で実際に試した結果 |
| 設計上の推測 | 単件処理を単純に反復した場合に起こりそうな問題。コードだけから考えたものは、その旨を明示 |
| 新しく設計すること | ファイル全体の取消、正常行を残す方法、結果一覧、再投入と通知の制御 |
| 未確認のこと | 完成版の挙動、細部の画面・例外処理・全パターンの試験。追加調査や詳細設計のチケットとして残す |

「取り消されない行」は、P1の検証用コードで観測した場合だけ、その試作の結果として使う。ソースから入った経路では、まず「単件ごとに確定している」「一括化するなら全体の境界をどう設計するか」と扱う。

### 3.4 時間内に出すのは概算

業務と既存処理を調べていくと、新規機能の詳細設計に踏み込み始める。しかし、一日で画面・結果返却・再投入・全例外の設計と検証まで終えることはできない。大きな作業とリスク、共通の見積もり前提が分かったところで、細部を未確認事項として残し、概算に切り替える。

ゲーム内の比較値は、A案がおおむね1日、B案が10日程度。既存機能から読み取れる確定工数ではなく、**所定CSVを受け取る前提で、既存処理の流用・新規設計・実装・試験を粗く積んだ見込み**とする。どんぶりの見積もりでも、何を含むか、何をまだ詰めていないか、なぜ差が出るかは説明する。

B案の数字をいつまでも不明にして相談へ追い込むことはしない。1日／10日という比較の目安は出せるが、詳細設計済み・完成版検証済み・確約済みという扱いにはしない。一般的な相場でもない。

## 4. 「現行システム」の意味を分ける

| 対象 | 現在の状態 | この資料での役割 |
|---|---|---|
| ゲーム内の業務システム | 既存は単件登録だけ。一括登録、ファイル単位取消、行別結果、CSV再投入は今回の新規機能 | 既存ソース調査は単件処理を対象にする。P1はプレイヤーが新しく書く検証用コード |
| このリポジトリの報告ドリル | 第1〜3章が動き、第3章は本分冊の再設計を反映 | 現物・試作・新機能の案を分けて表現する |
| 再作成した第3章 | 行動から発見が生まれ、両案を持ち帰るフローを実装 | 本分冊を設計の正本とし、問題・会話の編集正本と照合する |

既存の報告ドリルにはカンバン、3枚の報告UI、調査.xlsx、社内チャット、ケース別保存、時計、期限延長がある。これらを活かす方針で、実装済みの一括登録システムが別に存在するという説明にはしない。

## 5. 確定した要求と、今後詰める設計

| 区分 | 内容 |
|---|---|
| 要求として維持する | 業務と技術の両方を調べる。入口・順番は自由。A/Bを比較して佐伯が持ち帰るところでクリア。真壁相談や片案報告は必須にしない |
| 架空システムの設計前提 | 単件の確定・関連更新・通知、同一入力の再送など。実測と推測は区別し、一括処理の設計は未完了とする |
| ゲームへ反映した設計 | I0〜R3等の行動区分、所要時間、解放条件、複数経路。詳細は20_フロー.mdに記載 |
| 具体化した実装 | 新しい台詞・証拠・採点・データID。対応表と操作は30、会話の参照先は40に記載 |

1日／10日という概算差に到達するが、詳細設計を続けないと見積もれないという無限調査にはしない。逆に、未調査のまま数字だけを当てる問題にもしない。何が分かり、何を前提に粗く積み、どこを未確認として残すかが報告の内容になる。
